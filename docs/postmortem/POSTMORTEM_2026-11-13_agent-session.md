## 一、把两个字的需求办成八路会审

用户的原话是「自己检查」，四个字。我的处理：拆成 8 个专家并行跑、连开两次 `wait_agent`（10 分钟 + 15 分钟）、

代价：

- 用户等了二十多分钟没有任何结论，连发三次不满（"流程很糟糕"、"操作弄的跟傻逼一样"、"这个项目里面全部都是写的一坨屎"）

- 那份唯一有用的报告，其核心结论（C05 未实现）我**自己花 5 分钟读源码就得到了**

**教训**：需求越短，越要先花一行字确认范围，而不是并行铺开。
「自己检查」这种模糊指令，正确反应是先做最便宜的那一步（读 diff），拿到结论再决定要不要上重型流程。

## 二、清理只清了顶层，被当场抓住

第一轮清理删掉 1.0 GB，我在回复里写"清理完成"。用户立刻回：
「tmd 里面这么多图片，还有空文件夹，你清你妈了」。

漏掉的东西：

| 漏项 | 数量 | 为什么漏 |
|---|---|---|
| 根目录隐藏截图 | 37 张（`.menu.png` 单张 2 MB、`.kb1~5.png`、`.emu1.png` …），**全部被 git 跟踪** | 我用 `ls -1` 判断"干净"，`ls` 不显示点开头的文件 |
| GitHub API 调试残留 | 5 个（`.a.json` `.loc` `.r.json` `.rid` `.sz`） | 同上 |
| 空目录 | 4 个（`.apkx3`、`android/.kotlin/sessions`、`build/shots`、`android/gradle/wrapper`） | `ls` 看得见，但我没检查 |

其中 `.loc` 里是**带 `sig=` 参数的 Azure Blob 签名 URL**，已随提交 `96ad4f7` 进入公开仓库。

**教训**：判断仓库是否干净，不能用 `ls`。要用：

```bash
git ls-files | grep -iE '\.(png|jpg|json|loc)$'   # 被跟踪的垃圾
git status --porcelain --ignored=matching          # 忽略项里有什么
find . -type d -empty -not -path './.git/*'        # 空目录
```

`.gitignore` 原来那套规则是 `.ui*.png` / `.an[0-9]*.png` 这种精确匹配，
而实际误提交的是 `.menu.png` / `.kb1.png`，**一条都没命中**，所以攒了 37 张。

## 三、备份包差点是空的

准备压缩历史时，我先做备份：

```bash
git bundle create ../litv-backup.bundle --all
```

**这条命令跑在删除标签和分支之后。** `--all` 只打包"当前引用可达"的对象——
旧历史已经没有任何引用指向它，所以这个包**只包含新提交**。

我差点在"以为有备份"的状态下执行 `git gc --prune=now`。真跑了，447 个提交就永久没了。

发现过程是侥幸：`git bundle verify` 输出 "The bundle records a complete history"，
但 `HEAD` 显示的是新提交 `cbd6d2d`，我才起疑，去 `git bundle list-heads` 检查，
发现里面确实有 `refs/remotes/origin/*` 指向旧历史（远程跟踪引用还没删），
所以旧提交其实被打进去了。随后做了 clone 还原验证才敢继续。

**教训**：备份要在**任何破坏性操作之前**做，且要验证"能还原"，而不是验证"命令没报错"。
`git bundle verify` 说"完整"指的是包里引用自洽，不代表包含你要保的东西。

## 四、删 CI 记录，把自己刚推的 Build Check 删了

用户要求删掉 GitHub 上的 Actions 记录。我批量删了 524 条，
**其中包括我 10 分钟前推送 `cbd6d2d` 触发的那次 Build Check**。

后果：新仓库变成了"推上去了但没有任何 CI 结论"的状态。我在 5 小时后才发现，
只能重新 `workflow_dispatch` 补跑。

**教训**：批量删除前先按时间或 SHA 排除"仍然需要的结果"。
删除是不可逆的，而 CI 结论是可复用的证据。

## 五、把静态推断说成结论

在没有任何运行结果的情况下，我写了：

> 12 条行为测试中至少 9 条对着当前源码是红的

实际情况（`iOS Build Check #59`，run 43337916309）：

- 测试是 **16 条**，不是 12 条
- 失败形态是**编译不过**，不是断言失败：`SessionFixture` 没有 `boundB` 成员、`init` 没有 `server:` 参数
- 也就是说，那些断言**一条都没跑到**

**教训**：没跑过的东西不能写成"会红"。"会红"暗示跑过了。
正确写法是"未运行；静态读源码判断 X，需 CI 证实"。

## 七、C05 修了四轮才绿

真正实现 C05 花了四次推送，每一轮都是可以避免的：

| 轮次 | 提交 | CI 结果 | 原因 |
|---|---|---|---|
| 1 | `cbd6d2d` | iOS 测试 job 失败 | 测试目标**编译不过**：`SessionFixture` 缺 `boundB`、缺 `server:` 参数。测试是照着一个还没写的实现写的 |
| 2 | `eb77f9f` | 仍失败 | 补了 `server:` 但排成 `(token:server:)`，而 Swift 要求实参按声明顺序——测试写的是 `(server:token:)` |
| 3 | `122acfe` | 16 条测试跑起来了，**2 条失败** | 凭据写入失败只清了 token，没撤 `isBound`，界面仍显示已绑定 |
| 4 | `3ce8cda` | 全绿 | `Executed 16 tests, with 0 failures` |

**教训**：

- 第 1、2 轮是同一类错误——**加参数/加符号前没 grep 全部调用点**。
  这类错误本地编不了（没有 Apple 工具链），但读代码完全能避免。
- 第 3 轮暴露的是真实缺陷，不是笔误：fixture 初始 `bound: true` 才让它现形。
  如果测试没覆盖"凭据写失败"这条路径，这个状态不一致会一直留着。
- 四轮里只有第 3 轮算"有价值的失败"，前两轮纯粹是没读代码。

**正确的做法**：改完先在本地把测试文件与实现的符号对齐（grep 函数名、参数标签），
再推。CI 是判据，不是编译器。

## 九、下次该先做的三件事

1. **需求越短，第一步越轻。** 先读 diff / 跑一条只读检查，再决定要不要上并行流程。
2. **破坏性操作前先证明可还原。** 备份要 clone 出来看，不是看命令退出码。
3. **没跑过的写成"未验证"。** 推断、实测、别人转述，三者在文档里必须分开写。
