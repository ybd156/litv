# litv-edge

LITV2 的边缘降级部署：NAS 挂了之后，用 Cloudflare 免费额度顶住。

> **代码开源，实例私有。**
> 这个目录只放代码和文档，不含任何源地址——它们全在本仓库的 Actions Secrets 里。
> 部署工作流在仓库根的 `.github/workflows/edge-deploy.yml`，只改 `edge/` 才会触发。
>
> **安全边界**：源地址、Cloudflare token 都在 Secrets 里，不进代码、不进日志、
> 不进产物。生成的 `playlist.m3u` 被 `.gitignore` 挡着，不会入库。
> 但请注意：本仓库是 public，能拿到 Secrets 的只有仓库所有者——
> 如果以后加了有写权限的协作者，他们就能读走你的源地址和 Cloudflare 凭据。

做法不是"再造一个服务端"，而是**在边缘实现最小的一层 LITV 协议**，
让现有的 Android TV / 手机 / iOS 客户端以为自己在连 NAS——**客户端零改动**。

## 为什么能不改 app

客户端本来就留了两条路，正好够用：

| 机制 | 代码位置 |
|---|---|
| `/api/v1/tv/play/{id}` 返回 `mode="direct"` + 上游绝对地址 + `headers` 时，客户端自己直连源站 | `android/.../data/Api.kt` 的 `absolute()`、`Models.kt` 的 `PlayInfo.playHeaders()` |
| 绑定页本来就是「服务器地址 + 6 位数字绑定码」两个输入框 | `android/.../ui/BindActivity.kt`、`ios/.../BindView.swift` |

所以这里**只实现协议，不碰任何媒体字节**：没有中转、没有 ffmpeg、没有磁盘。
播放时服务端把上游地址原样给客户端，流量完全不经过 Cloudflare。

```
客户端 ──HTTP──> Workers（频道表 / 线路表 / 设备 token / 管理台 API）
   └──────────── 直连 ────────────> 上游源站
```

## 组成

| 部分 | 位置 | 说明 |
|---|---|---|
| 抓取与生成 | `scripts/build.mjs` | 拉订阅 m3u → 去重合并 → 产出 `playlist.m3u` 和 `sql/seed.sql` |
| 边缘 API | `src/index.ts` | 最小 litvd 协议 + 管理台后端 |
| bootstrap 响应体 | `src/bootstrap.sql.js` | 在 SQLite 里直接拼 JSON，Worker 只吐字节（见「频道数」一节） |
| 管理台 | `public/admin.html` | 单文件、无构建、无外部依赖 |
| 存储 | D1 | 频道 / 线路 / 设备 / 人工覆盖 / 收藏 / 续播 / 设备配置 |
| 自测 | `scripts/selftest.mjs` | m3u 链路 + 内存 SQLite 端到端，69 条断言 |

## 源格式：填什么它认什么

`SOURCE_URLS` 里填的地址，脚本会**自己嗅探格式**，不用你指定：

| 拿到的东西 | 处理 |
|---|---|
| `#EXTM3U` / `#EXTINF` 开头 | 按 M3U 解析（支持 `tvg-id`、`group-title`、`#EXTVLCOPT` 的 UA/Referer） |
| `分组,#genre#` + `频道名,地址` | 按 TXT 解析。**自动识别 GBK**，国内这类源大多不是 UTF-8 |
| 网页（HTML） | 跳过并提示：你填的是面板首页，需要"订阅/播放列表"地址 |
| JSON | 跳过并提示：这是面板 API，不是播放列表 |
| 认不出来 | 跳过，并打印开头一小段（地址已脱敏）帮你定位 |

判据和 [server/internal/parse](../server/internal/parse/parse.go) 里的 `Detect()` 保持一致，
不另立一套规则。名字里带逗号的情况按"从右往左找第一个紧跟协议头的逗号"拆，
`rtp://`、`udp://` 这些内网协议也认。

**单个源失败不会拖垮整体**：其它源解析成功就照常生成；只有**全部**源都没解析出条目时
才 exit 1（宁可让部署失败，也不拿空列表覆盖线上的好数据）。

暂不支持 TVBox 的 `{"lives":[...]}` JSON 格式。

## 节目单

源的 m3u 头里如果写了 `x-tvg-url`，CI 会自动把节目单一起拉下来：

```
#EXTM3U x-tvg-url="https://epg.example.org/t.xml"
```

| 环节 | 做法 |
|---|---|
| 拉取 | CI 拉 XMLTV（实测 6.5MB / 135 频道 / 3.2 万条），解析后只留**前后几天的窗口** |
| 匹配 | 你的 m3u 大多没有 `tvg-id`，所以按**频道名**匹配：先归一化精确相等，再取**最长前缀** |
| 入库 | 写进 `epg_programs`（整表替换），并把匹配到的 id 回写到 `channels.epg_id` |
| 下发 | `/api/v1/tv/epg/{id}?day=N`，日边界按 `Asia/Shanghai` 算好，连 `day_start`/`day_end`/`timezone` 一起给客户端 |

**为什么最长前缀很重要**：`CCTV1` 是 `CCTV10`~`CCTV19` 的前缀，
按第一个命中匹配的话，CCTV-10 会显示 CCTV-1 的节目。自测里有一条专门盯这个。

**刷新频率是每天一次，和重建同频。** D1 免费版每天只给 10 万行写入，
一次全量节目单就是几千行——跟着小时级重建跑，光节目单一天就吃掉一大截，
**那额度是部署者自己的**。所以 `build.mjs` 会读 `kv.last_epg_at` 自己限速。

**匹配不上的频道**（节目源没覆盖）会返回 `note: "该频道未关联 EPG"`，
客户端显示"暂无节目单"，不是报错。

**入库是按 `channels.id` 关联的**，所以频道 id 必须跨重建稳定，否则节目单会
整批挂空（见下面「手工改动不会被每日重建冲掉」一节）。

## 部署

和 LITV2 同一个仓库，工作流已经在 `.github/workflows/edge-deploy.yml`，
不用另建仓库、不用改路径。

### 1. D1 数据库

本仓库已经建好并写进 `wrangler.toml`（`database_id` 是标识不是凭据，
提交进仓库没有风险）。要换成你自己的库：

控制台 → Workers & Pages → **D1** → Create database，名字 `litv-edge`，
把返回的 UUID 填进 `wrangler.toml` 的 `database_id`。

（也可以用 `npx wrangler d1 create litv-edge`，但没必要为这一步在本机装环境。）

### 2. 配 Secrets

本仓库 Settings → Secrets and variables → Actions：

| Secret | 必需 | 说明 |
|---|---|---|
| `BIND_CODE` | ✅ | **必须是 6 位数字**（客户端输入框限死了）。电视绑定码，**只管设备绑定** |
| `ADMIN_PASSWORD` | ✅ | 管理台登录口令。**必须配**：绑定码不能当管理台口令（见下面的说明）。没配的话管理台登不进去，部署时 Actions 会给一条警告 |
| `ADMIN_PATH` | 可选 | 管理台入口路径（如 `litv-9f3a`）。留空 = 根路径就是入口（Vue 版）、`/admin.html` 是单文件备用台。填了之后只有 `/<这个名字>` 能打开（Vue 版），备用台挪到 `/<这个名字>/simple`，根路径 / `/index.html` / `/admin.html` 一律 404。只接受字母/数字/下划线/短横线（单段）。**CI 只在这个值非空时才写进 Worker**——要取消入口去 Worker 那边 `wrangler secret delete ADMIN_PATH`，别指望删 secret 就自动清空 |
| `CLOUDFLARE_API_TOKEN` | ✅ | Cloudflare → API Tokens。模板用 "Edit Cloudflare Workers"，**再手动加 Account → D1 → Edit** |
| `CLOUDFLARE_ACCOUNT_ID` | ✅ | 控制台右侧栏的 Account ID |
| `DISPATCH_TOKEN` | 可选 | 配了管理台才有「立即重建」按钮。fine-grained PAT，只给本仓库的 **Actions: write**。**注意名字**：GitHub 不允许 secret 名以 `GITHUB_` 开头（会直接拒存），所以 GitHub 这边叫 `DISPATCH_TOKEN`；CI 写进 Worker 时再改成 `GITHUB_DISPATCH_TOKEN`。 |
| `SOURCE_URLS` | 回退 | 一行一个地址。**推荐在管理台的「源」页里配**，这里只是没有 UI 时的兜底 |
| `SOURCE_UA` | 回退 | 全局 UA。**两个用途**：① 拉订阅时的请求头；② 作为每条线路的**播放兜底 UA** 下发给客户端。很多面板对拉取宽松、对播放分片严格，只配拉取会表现为「能导入、客户端播不了」——这种情况就在这里填播放器要的 UA（比如 `okHttp/Mod-1.5.0.0`）。每个源自己的 UA 在「源」页里配，优先级更高 |

> **为什么 `ADMIN_PASSWORD` 是必需的**：绑定码只有 6 位数字（100 万种可能），
> 会显示在电视绑定页、家里每个人都要输入、还可能被截图。拿它当管理台口令
> 等于把管理权限压在一个短数字上。所以两者彻底分开：
> `BIND_CODE` 只管设备绑定，管理台只认 `ADMIN_PASSWORD`。
> 这个改动会让**只配了 BIND_CODE 的老部署登不进管理台**——去补一个 `ADMIN_PASSWORD` 就好。

> **绑定码忘了去哪儿看**：管理台的「终端设备」页顶部就有，默认打码成 `12•••56`，
> 点「显示」才看明文（要登录才拿得到）。入口地址也显示在那里。

> **源不放这里。** 订阅源是日常要改的东西，放在管理台的「源」页（存在 D1），
> 每个源可以带自己的 UA / Referer。`SOURCE_URLS` 只在 D1 里一个源都没有时才用。

### 3. 跑一次

Actions → `Edge Deploy` → Run workflow。它会先跑 `check`（类型检查 + 自测 + 打包检查），
全绿才部署。

只改 `edge/` 或 `admin/` 的提交会自动触发。

| 字段 | 填什么 |
|---|---|
| 服务器地址 | 切到"用域名访问"，填 `https://litv-edge.<你的子域>.workers.dev` |
| 绑定码 | 那 6 位数字 |

第三方播放器（可选）：


### 屏蔽（比逐个「隐藏」省事）

在自带管理台的左边栏「屏蔽」页里（**只有边缘部署有这一页**，NAS 服务端没有这个接口）。

订阅源里几百个台，购物 / 测试 / 成人这类整类不想要。管理台的「隐藏」是**逐个频道**
点，而源每周都会加新的同类频道，藏完还得再藏一遍——所以有「屏蔽」页：

| 屏蔽什么 | 行为 |
|---|---|
| 分组（如「购物」） | 该分组下**所有**频道都不再下发，包括以后新加的；分组也不再出现在统计里 |
| 频道名（精确匹配） | 只挡这一个台；改过名的频道按**改后的名字**匹配 |

分类列表是**从源里读出来的**（带频道数，数字只算"会下发的"，和点进去看到的条数一致），
点一下「屏蔽这个分类」就行，不用手打分组名。已屏蔽的分类留在原位、标「已屏蔽」，
按钮变成「解除屏蔽」——源里已经下架的分类也会补一条 count 0 留着，否则重建后
就再也找不到它、没法解除。

生效时机有两层，缺一不可：

1. **Worker 查询里直接过滤** —— 点完立刻生效，不用等重建（客户端下次拉列表就没了）；
2. **CI 生成时就过滤** —— 这些频道根本不入库、也不进 `playlist.m3u`，顺带少占 D1 的行数。

清单存在 `kv` 的 `blocked` 那一行（一段 JSON），**没有新建表**：这份清单只在管理台
改配置时才变，多一张表就多一次查询、多一份迁移要维护。Worker 侧用非相关子查询
取值（SQLite 只算一次），所以给每个频道都带上两个条件也不增加查询次数。
CI 那边和 `last_build` 合并成**一条** `SELECT`，不额外花查询。

清单被手改坏时按「什么都没屏蔽」处理，而不是让整个 bootstrap 崩掉。

**缩水护栏比的是屏蔽之前**的条目数：用户主动屏蔽一整类会让频道数下降，那不是故障。

## 管理台

**用的是 LITV2 自带的管理台**（`admin/` 的 Vue 应用），不是另写一套。
CI 会把它构建出来（`--base=/`）塞进静态资源，访问根路径就是：

```
https://litv-edge.<你的子域>.workers.dev/
```

登录页和 NAS 上那个一模一样：品牌方块 + 主机名 + 口令。口令是 `ADMIN_PASSWORD`；
没配这个 secret 时才回落到 `BIND_CODE`（不推荐，见上面的说明）。

**能用的**：源（增删改、每源自己的 UA/Referer、测试连通）、频道（搜索/分组/改名/
启用停用/批量/拖拽排序/线路增删）、**屏蔽（整类 / 单台）**、设备（查看、吊销、下发配置）、
概览、EPG 查看与搜索、立即重建。

**左侧导航里看不到的**（边缘版没有对应物，直接不显示，直接敲 `#/live` 会被踢回概览）：
**直播预览**（要 NAS 的 `/web/play` 中转，边缘只有直连）、**系统设置**
（配置在 `wrangler.toml` 和 Secrets 里，接口一律 2006）。
留着入口只会让人以为是自己的配置错了。

**明确不支持的**（点了会提示"边缘模式不支持"，不会假装成功）：
EPG 导入与映射、台标抓取/上传、**设备审批**、系统配置、系统日志。
这些在边缘架构里没有对应物——不是没做，是本来就不存在。

（"下发配置"是支持的：它只需要把 JSON 存进 D1 再推进 `config_version`，
不需要审批流程，也不需要长连接。）

### 源和「立即重建」

- 源存在 D1 里，在「源」页改完就保存
- 抓取 + 解析要跑 CI（免费版 Worker 单次只有 10ms CPU，解析不了播放列表）
- 配了 `DISPATCH_TOKEN` 就能点「立即重建」，否则等每天 03:00（北京时间）
- **改 UA 不需要重建**：`ua` 是播放时属性，`/tv/play` 会实时读源配置
  （单源部署下立刻生效；多源部署回落到重建时的快照，因为那时才能确定
  每条线路来自哪个源）。改完 UA 让客户端重开一次即可——
  Android 的播放结果缓存 5 分钟。

**「立即重建」点不动 / 点了没反应，按这个顺序查**：

| 界面上的表现 | 原因 |
|---|---|
| 按钮是灰的，悬停有提示 | 缺 `DISPATCH_TOKEN`（或 `GITHUB_REPO`），提示里会写缺哪个 |
| 在 Secrets 页面存不进去，报「must not start with GITHUB_」 | 你在用 `GITHUB_DISPATCH_TOKEN` 建 secret。**GitHub 侧的名字是 `DISPATCH_TOKEN`**，带 `GITHUB_` 前缀只是 Worker 内部的环境变量名 |
| 红条「令牌无效或已过期」 | PAT 过期了，重新生成一个复制进 Secrets |
| 红条「令牌权限不够」 | fine-grained PAT 要为**这个仓库**勾上 `Actions: write` |
| 红条「仓库或工作流不存在」 | 提示里会打印实际在打哪个仓库 · 工作流 · 分支 |
| 红条「分支不存在」 | `GITHUB_REF` 要和默认分支一致 |

仓库 / 工作流 / 分支由 CI 部署时用 `--var` 写进 Worker（取 `github.repository`
等），所以 fork 出去不用改代码；本地手动 `wrangler deploy` 时用 `wrangler.toml`
里 `[vars]` 的兜底值。

### 简易版管理台（备用）

`/admin.html` 还留着一个单文件版本，功能更少但没有构建依赖。
自带管理台出问题时可以用它兜底。配了 `ADMIN_PATH` 之后它的地址变成
`/<入口>/simple`（不再占一个能猜到的公开路径）。

它的登录框以前把口令限死成"6 位数字"（`maxlength="6" inputmode="numeric"`），
配了 `ADMIN_PASSWORD` 就永远登不上——现在没有这个限制了，提示文案也分成
"配了 ADMIN_PASSWORD" 和"没配、退回 BIND_CODE"两种。

### 手工改动不会被每日重建冲掉

这是整套东西里最容易踩的坑。数据分成两类：

| 列 | 含义 |
|---|---|
| `channels.stable_key` | 跨重建稳定的标识（`id:<tvg-id>` 或 `name:<归一化频道名>`） |
| `channels.origin` | `m3u` = 订阅生成；`manual` = 管理台手工加 |
| `streams.origin` | 同上 |
| `streams.channel_key` | 让手工线路在重建后还能挂回正确频道 |
| `channel_overrides` | 对订阅频道的改名/改分组/隐藏，按 `stable_key` 存 |

重建顺序：清订阅线路 → **upsert 频道**（不删不重建）→ 手工线路兜底重挂 →
插新线路 → 清掉订阅里已经消失的频道。所以：

- 订阅频道的改动存进 `channel_overrides`，重建后照样生效
- 手工添加的频道和线路不受重建影响
- **拖拽排序也不会被擦掉**：`channels.sort` 不参与 upsert 的更新列，
  否则每小时一次的订阅顺序覆盖会把管理台里排好的顺序抹平
- 订阅频道删不掉（下次还会回来），管理台的"删除"对它是**隐藏**
- 手工线路如果挂的频道从订阅里消失了，会被跳过而不是挂成空频道

**频道 id 必须跨重建稳定。** 以前是"删了重插"，`AUTOINCREMENT` 让 `channels.id`
每次都变，而 `epg_programs.channel_id` 存的是这个数值 id、节目单又是 6 小时才
整表重刷一次——于是 6 小时里有 5 小时节目单全挂在已经不存在的 id 上，客户端
一直显示"暂无节目单"。现在改成 `ON CONFLICT(stable_key) DO UPDATE`，
id 不再变；`epg_id` 和 `enabled` 刻意不参与更新（前者由节目单任务回写，
后者是管理台"隐藏"的结果，覆盖等于撤销用户操作）。

**频道数突然缩水会被拦下来。** 只挡"全部源都失败"是不够的：单个源半失败、
只剩几条时，生成是"成功"的，一旦写进去线上每小时都是残的。

判据不是「数字变小了」——**换源 / 删源本来就会让数字变小**，那是正常操作。
真正的判据是「源配置有没有变」：

| 情况 | 处理 |
|---|---|
| 上次记录里没有源集合（旧版本写的，升级后第一次） | 放行，并记一条日志 |
| 源集合变了（增删源、换订阅）且这次没有源报错 | 放行，按正常变更处理 |
| 源集合没变，但有源拉取失败 | **拦**（这才是故障信号，报错里会点名是哪个源） |
| 源集合没变、全部成功，条目却暴跌 | **拦**（源端内容异常） |

`kv.last_build` 里记了 `source_ids`，就是给这条用的。

极端情况下要强行写入（比如确认源端就是要大幅裁减）：仓库
Settings → Secrets and variables → Actions → **Variables** 加 `ALLOW_SHRINK=1`
再重跑。用 variable 不用 secret——它不机密，值在日志里看得见也好排查。
**放行完记得删掉**，否则护栏永久失效。

失败原因会直接贴在那次 Actions 运行的 **Summary** 页面，同时打一条
annotation（不用翻原始日志）。

## 硬限制（先看清楚再决定）

**1. 上游必须公网可达。** 内网源、UDP 组播源、绑运营商线路 IP 的源，边缘模式下
一律拉不到——没有中转就没有任何补救手段。这是这个方案最大的天花板。

**1.5 带 sign 的源必须高频重建。** 不少面板在 m3u 里下发的是**带签名的临时地址**
（`?userid=…&sign=…&auth_token=…`），每次拉取都会换一批、而且会过期。
因为不中转，客户端拿到的是这份快照，签名过期就播不动。
所以定时重建是**每天 03:00** 一次（实测面板地址 98 分钟后仍有效，
一天一换够用）。如果你的源签名有效期更短，就加密 cron、点「立即重建」，
或者接受"过期之后要手动刷一次"。

**2. 频道数上限不在 Worker，在客户端。** 免费版每次请求只有 10ms CPU，
所以 `bootstrap` 的 JSON **不是在 JS 里拼的**——整个响应体由
`src/bootstrap.sql.js` 在 SQLite 里拼成字符串，Worker 只做"取一行、吐字节"，
CPU 开销与频道数无关。D1 的查询耗时算 wall time，不占那 10ms。

实测（本地 SQLite，仅代表规模量级）：

| 频道数 | 响应体 | SQL 耗时 |
|---|---|---|
| 500 | 0.10 MB | 1.6 ms |
| 2000 | 0.39 MB | 5.6 ms |
| 5000 | 0.99 MB | 12.4 ms |
| 10000 | 1.99 MB | 22.7 ms |

真正的天花板是**客户端**：几 MB 的 JSON 丢给电视盒子解析会明显拖慢启动，
D1 单行/响应体也有大小限制。**几百到两千个频道是舒适区**，
超过五千要开始考虑裁掉隐藏频道或按分组拆。

注意：`ORDER BY` 在聚合函数里的顺序依赖 SQLite 的实际行为（`selftest` 有断言），
不是文档承诺——万一哪天顺序乱了，只是频道排序不对，不会坏。

**3. 探活结果是边缘视角。** 管理台"测试"按钮是从 Cloudflare 边缘发的请求，
通了不代表你家能播。只能当参考。

**4. 没有扇出。** 每台设备各自连上游。上游限制并发时会互踢，这个无解。

**5. 绑定码是 6 位数字，空间只有 100 万。** 设备注册和管理台登录都按 IP 做了
失败限速（10 次 / 10 分钟），`playlist.m3u` 用独立的桶（20 次 / 1 分钟，
窗口更短，避免旧客户端拿着作废的绑定码把同一出口 IP 的用户锁太久）。
即便如此，也不要把 workers.dev 地址到处发。

**6. `*.workers.dev` 在国内不稳定。** 建议绑自己的域名，并在目标网络实测。

**7. 播放统计的写入被丢弃。** 概览页没有「今日起播次数」这类数字。
收藏和续播是**真的存**的（见上面支持情况表）；被丢掉的只有播放上报
（`/tv/stats`）——边缘没有统计页，存了也没人看，反而要花 D1 的写入额度。

## 资源与额度（每个请求花掉什么）

免费版的三个硬上限决定了代码怎么写：**10ms CPU / 请求**、**50 subrequest / 请求**、
**D1 每天 10 万行写入**。下面这张表就是"一次请求实际花掉什么"：

| 接口 | D1 往返 | 写入行数 | 读行数（500 频道 / 800 线路 / 3 万 EPG） |
|---|---|---|---|
| `/api/v1/health` | 0 | 0 | 0 |
| `/api/v1/tv/bootstrap` | **1** | 0 | **≈ 3.0k**（优化前 ≈ 32k） |
| `/api/v1/tv/heartbeat` | 2 | 0~2（条件写） | 1 |
| `/api/v1/tv/play` `streams` `epg` | 1~2 | 0 | 个位数 |
| `/api/v1/tv/favorite` `progress` | 2 | 1 | 1 |
| `/playlist.m3u` | 1 | 0（只有猜错才记一行） | 1 |
| 管理台读接口 | 2~3 | 0 | 按页 |

**bootstrap 是唯一的大头，所以专门抠过**（本地 SQLite 实测 7.09ms → 2.26ms）：

| 问题 | 以前 | 现在 |
|---|---|---|
| 节目单 | `start_at <= now AND end_at > now` → **全表扫**（3 万行/次） | 加下界 `start_at >= now-6h`，走 `idx_epg_time` 范围扫（≈1.2k 行） |
| 每个频道的线路数 | `(SELECT COUNT(*) FROM streams WHERE channel_id = c.id)` → **N+1（500 次）** | 一次 `MATERIALIZED` 聚合 + `LEFT JOIN` |
| 屏蔽清单 | 每个 `WHERE` 都 `json_each` 重新求值 → **上千次虚拟表扫描读同一行** | `MATERIALIZED` CTE 只解析一次 |
| `last_seen` | bootstrap 也写一次（外加一次往返） | **不写了**，在线状态由心跳维护 |

结果：单次读行数约 **32k → 3k（-90%）**，往返 2 → 1。

几条刻意的取舍：

- **心跳是最热的请求**（设备 30 秒一次）：两条写语句合并成一次 `batch`，而且都带
  "条件不成立就不写"——`last_seen` 4 分钟内不重写、`app_version` 没变不写。
  两个版本号一次读回来，少一次跨区域往返。
- **bootstrap 不写库**：设备在线状态由 30 秒一次的心跳维护，bootstrap 再写一次
  是纯浪费（每次启动多一次往返）。去掉它不影响「在线」判定的准确性。
- **`playlist.m3u` 是"先读、错了才写"**：以前每个正常请求都要 `INSERT` 一行再
  `DELETE` 一行，第三方播放器每隔几分钟拉一次就能吃掉一大截写入额度。
  现在只有猜错才记账、猜对就清掉，限速能力不变（被挡住期间连写都不写）。
- **`channels_version` 用 kv 计数器，不是服务端那样的全表指纹**：指纹要扫全表，
  而心跳 30 秒一次，D1 的读取额度扛不住（服务端跑在 NAS 本地 SQLite 上没这个问题）。
  代价是"要在写入点 +1"，所以推进动作放在**路由层按路径判断**：只有真正改频道表的
  写操作才推进。改源、下发设备配置不推进——否则每改一次配置，所有电视都白拉一遍列表。
- **bootstrap 的响应体在 SQL 里拼**：Worker 侧只剩"取一行、吐字节"，
  CPU 开销与频道数无关。
- **分页接口**（`admin/channels` / `tv/channels`）刻意**不用**预聚合 JOIN：
  它们带 `LIMIT`，N+1 只查当前页那几十行，而预聚合要扫全表 streams——
  分页场景下 N+1 反而更省。只有 bootstrap 这种"一次要全量"的才值得换成 JOIN。
- **CI 侧并发抓源**（默认 4 个，`FETCH_CONCURRENCY` 可调）：串行的话源多就是
  N 次 TLS 握手相加。
- 限速表 `bind_attempts` 只增不删会越积越多，所以每小时重建时顺手清掉一天前的行。

## 安全说明

- 设备 token 服务端只存 SHA-256 哈希，不存明文
- 管理台会话也是哈希存储，带 7 天过期
- **管理台只认 `ADMIN_PASSWORD`，绑定码不能登录**。绑定码是 6 位数字、
  要公开给家人输入，拿它当管理口令等于把管理权限压在一个短数字上
- **绑定码默认打码**（`12•••56`），要看明文得已登录 + 显式点「显示」
  （`?reveal=1`），不会在每次打开页面时自动拉下来
- **入口路径可自定义**（`ADMIN_PATH`）：配了之后根路径与 `/admin.html`
  一律 404，只有那一个路径能拿到登录页，单文件备用台挪到 `/<入口>/simple`。
  这不是强安全（API 仍在 `/api/` 下），挡的是碰运气的扫描。
  非法值（含 `..`、`/`、编码字符）会被忽略、退回默认入口
- **`[assets] html_handling = "none"` 是这条的硬前提**：默认的自动 html 处理会把
  `/` 映射到 index.html、把 `/admin.html` 307 到 `/admin`，而且都发生在**跑 Worker
  之前**——不关掉它，入口控制对 `/` 完全失效（线上实测确认过）
- 同一个 `device_key` 换平台注册会被拒绝（对齐真服务端的 `ErrDeviceKeyConflict`；
  比较时忽略大小写，兼容早期写进库的混合大小写值）
- `platform` 只用于展示与冲突检测，统一 trim/小写/截断，保留值 `admin` 拒绝，
  **不参与鉴权**
- 绑定码错误按 IP 限速，防暴力枚举
- `playlist.m3u` 里有上游地址，和接口同等级保护（`?t=` 校验），错了一律 404；
  按 IP 限速 20 次 / 1 分钟，超限期间即使 `t` 正确也先 404
- 管理台把频道名当不可信输入转义后再渲染（名字来自上游 m3u）
- **错误码按语义分开**：未认证是 `2001` + HTTP 401（管理台只认这个组合，
  才会把你送回登录页）；参数不对是 `1001`；设备未绑定是 `2003`。
  混用会让人填错一个源地址就被整页踢到"未授权"上
- **限速按用途分桶**：`bind:`（设备绑定）、`admin:`（管理台登录）、
  `playlist:`（播放列表）三个独立计数。共用一个桶时，家里电视输错 10 次
  绑定码会连带把管理台登录锁 10 分钟
- **出站抓取有目标校验**（`src/net.ts`，Worker 与 CI 共用）：只允许
  http/https；拒绝本机、内网、链路本地（含云元数据 `169.254.169.254`）与
  `.local` / `.internal` 域名；跳转自己跟进**逐跳**校验。探活、测源、
  CI 抓订阅、CI 抓节目单走的是同一套
- **这套校验的边界**：Workers 里拿不到 DNS 解析结果，域名解析到内网拦不住。
  兜底是 Cloudflare 边缘到私网本来就不通——这也是"上游必须公网可达"那条限制
  的另一面
- **没做的**：设备 token 没有有效期。换 `BIND_CODE` 只影响新注册，
  已发出的 token 仍然可用；要吊销得在管理台逐台删设备

## 开发

**不要在本机搭环境。** 按 LITV2 的 AGENTS.md §8，依赖安装、类型检查、自测、
打包检查全部在 `Edge Deploy` 的 `check` 任务里跑，本地只看 Actions 结论。

`check` 里依次执行：

```
npm ci --no-audit --no-fund
npm run typecheck                      # tsc --noEmit
npm test                               # selftest.mjs（抓取/生成）+ workertest.mjs（Worker 本体）
wrangler deploy --dry-run --outdir=.wrangler/dry
```

`scripts/selftest.mjs` 覆盖抓取与生成逻辑（69 条断言）；`scripts/workertest.mjs`
直接 import `src/index.ts`，用 `node:sqlite` 顶替 D1，所以限速 SQL、平台校验、
口令优先级、注销、playlist 鉴权、设备 token 打 `/tv/*` 的主链路**会真的执行**
（98 处 `check`，含循环展开实跑 135 条）。改 Worker 行为时两边都要看。

自测用的 D1 替身实现了 `batch`（真事务）和 `meta.last_row_id` / `meta.changes`
——这两样缺一个，批量操作和"注册返回 device_id"这类链路就等于从没被测过。

自测要连本地 `127.0.0.1` 的 fixture 服务器，而出站校验默认拦内网地址，所以
`selftest.mjs` 给子进程设了 `EDGE_ALLOW_PRIVATE_FETCH=1`。**只有自测会设**，
部署 job 不设；Worker 运行时也没有 `process`，这条路在线上走不通。
