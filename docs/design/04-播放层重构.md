## 1. 结论

1. **不做整体重写，做「分层剥离 + 契约收敛」。**
   `PlayerManager.kt`（1100 行）的病因不是"太长"，而是**三类不同生命周期的状态混在一个类里，且没有代际令牌**：会话（用户意图）、尝试（本次内核）、渲染（Surface）。注释里记录的真机事故（"匿名 Runnable 释放后仍 startEngine"、"attach() 不重置 prepared 导致 budgetWatchdog 直接 return"、"playChannel 后 179ms 就报 4 秒无数据"）根因都是这三类混用。

2. **本轮可以做到「零 Go 改动、零新字段、零信封变更」。**
   播放层需要的服务端字段（`kind/mode/url/expires/stream_id/headers/ua`、`server_time/channels_version/config_version`、QoE 8 字段）**已经全都有了**。缺的是客户端没解码、或解错了。

3. **动播放层之前必须先修 4 处已存在的契约漂移**，否则重构会把错误固化。其中最严重的是 `watch_ms` 单位错 1000 倍——它直接让"卡顿率"这个指标永久失真，而卡顿看门狗正是本次重构的目标之一。

4. **现状并非一片混乱**：`reportsFirstFrame` 能力位、`EngineChain` 降级链、`PlayRequestGate` 代际闸门、`PlaybackDefaults` 的"约束而非数字"断言、`isStalled` 纯函数 + 单测——这些都是正确的设计，重构要**继承**而不是推翻。

## 3. 错误分类与处置（双端同一张表）

现状问题：`onError(message: String)` 把错误降级成字符串，上层用 **16 个英文关键词做子串匹配**（`isNetworkFailure`）。跨语言、不可测，且 **HTTP 403 不在关键词表里** → 403 被判成非网络失败 → 换内核 → 三个内核轮一遍 → 报"所有内核均失败"。403 的真实含义是"签名过期/无权限"，正确处置是**重新取地址**，换内核永远修不好。

| FailureCode | key | 处置 | 不这么做的后果（已发生过的真机事故） |
|---|---|---|---|
| `TRANSPORT` | `transport` | `RETRY_SAME`（有上限）→ 耗尽 `GIVE_UP` | 以前换内核，把可用内核一个个烧掉 |
| `HTTP_AUTH`（401/403） | `http_auth` | **`REACQUIRE_URL`** | 现在不在关键词表里 → 换内核 → "所有内核均失败" |
| `HTTP_STATUS`（其他 4xx/5xx） | `http_status` | `NEXT_LINE` | 同一条坏线路重试多少次都一样 |
| `TIMEOUT_NO_BYTE` | `timeout_no_byte` | `RETRY_SAME`×1 → `NEXT_ENGINE` | — |
| `TIMEOUT_NO_FRAME` | `timeout_no_frame` | `SOFT_DECODE`（仅 Exo）→ `NEXT_ENGINE` | Amlogic 硬解喂数据不吐帧 |
| `DECODER_INIT` / `DECODER_RUNTIME` / `UNSUPPORTED_FORMAT` | — | `SOFT_DECODE` → `NEXT_ENGINE` | — |
| `SURFACE_LOST` | `surface_lost` | `REATTACH_SURFACE`（**绝不降级**） | 降级会把能播的台判死 |
| `LIVE_WINDOW_BEHIND` | `live_window_behind` | `SEEK_LIVE`（不是失败） | `ExoEngine.kt:532-545` 已修过一次 |
| `ENDED_UNEXPECTEDLY` | `ended_unexpectedly` | `RETRY_SAME`（有上限） | — |
| `UNKNOWN` | `unknown` | `NEXT_ENGINE` | 认不出当非网络失败，宁多试一次 |

**另加两类（安全侧要求）**：`TLS`（证书/主机名校验失败）→ **直接 `GIVE_UP`，绝不重试**。现状 `isNetworkFailure` 的 marks 含 `"ssl"/"handshake"` → 证书失败被重试 5×5s=25s，最后报"网络不可用"，掩盖真因，还会诱导人去关校验（硬约束禁止）。

**重试预算契约化**：现状 4 个独立计数器（`retried` / `endedRetries` / `netRetry` / `stallRecovered`）复位规则各不相同，没有统一上限。合并为 `RetryBudget(maxAttempts, maxWallClockMs)`，对外只需两句可观测承诺：① 总尝试次数 ≤ N；② 总耗时 ≤ `START_BUDGET_MS`（36s）。

**错误分类表是安全属性，不是 UI 细节**：把"该放弃"错判成"换线"= 无限重试；把"该换线"错判成"放弃"= 可用性事故。所以它必须有唯一一份真源 + 两端测试各自断言"每个枚举都有处置"。

| 事件 | sessionEpoch | renderEpoch | 预算 |
|---|---|---|---|
| 换台 | +1 | +1 | 重置 |

**现状的具体竞态缺陷**：`if (currentKind != kind) return@post`（`PlayerManager.kt:816/845`）在**换台后仍是同一 EngineKind** 时完全失效——旧台的 `onError` 会被当成新台的错误，直接 `tryNext` 把新台判死。`PlayRequestGate` 只挡了 API 响应顺序，没挡引擎事件。

**去重必须重做**：`PlayerManager.kt:644-647` 明确写着"去重暂时关闭…我没定位到是哪条"。重构时应把"起播"收敛成状态机的一个 `Effect.StartEngine`，同一 generation 内天然幂等，而不是加时间窗去重。

### 8.5 落地时踩到的一个坑（值得记住）

给 iOS `PlayInfo` 加 `stream_id` 时，第一版只做了两件事：加属性 + 加 `CodingKeys`。
**字段契约检查器变成了绿的，但字段实际永远是 0** —— 因为 `PlayInfo` 有**手写**的
`init(from:)`（`Models.swift:374`），Swift 合成的解码器根本不参与，
`CodingKeys` 只是给手写解码器用的键名表。

这类"假的绿"是最贵的：grep 型门禁全过、类型检查全过、CI 全绿，
而线上那个值从来没被赋过。所以检查器补了一条 **R5**：文件里存在手写
`init(from:)` 时，字段必须在其中出现为 `litv(.field)` 或 `forKey: .field`，
只有 `CodingKeys` 一行不算。

同理 `HeartbeatResult` 原来没有手写解码器，加字段后会走合成解码 ——
而 Swift 合成解码**不会用属性默认值**，键缺失直接 throw。于是顺手给它补了
逐字段 `decodeIfPresent`，与 `Models.swift` 里其它 DTO 的约定一致
（"新 App + 老 NAS"不该在心跳上抛错，心跳是静默的，出错没有任何界面提示）。

### 8.6 门禁的一条重要前提：它是**清单驱动**的

R5 上线后又做了一次负向验证（临时副本里删掉 `streamId = try c.litv(...)`）：
`exit 1` + `FAIL [R5] … 字段 "stream_id" 没在里面解出——（streamId）`，**规则有牙齿**。
同时用"原样复制不改"作负对照拿到 `exit 0`，排除了"临时根路径推导失败导致的假红"。

> **R1 / R5 只检查 `client_fields.json` 里登记过的字段。**
> 新增线上字段却忘了先登记，这两个检查会一起**沉默**——不是报错，是压根不看。

## 11. 真机卡顿归因（进行中，2026-11-17 凌晨）

**症状**（用户原话）：「都会播放一下卡一下」，表现为**画面顿住一下再跳/黑一下**，声音可能也断。
用户确认：**在我装新包之前就有**，不是本轮改动引入的。

**设备**：一台 arm64 手机，Android 13 / SDK 33 / 分辨率 1220×2712（型号与 IP 按 §8 不写进仓库）。

### 11.1 已采集的硬证据

```
02:41:14.185 E/VLC  libvlc input: ES_OUT_SET_(GROUP_)PCR  is called too late (pts_delay increased to 1000 ms)
02:41:14.223 E/VLC  libvlc decoder: output: 2130708361 unknown, 1920x1080 stride 0 0, crop 0 0 0 0
02:41:21.967 E/VLC  ... (pts_delay increased to 4692 ms)
02:41:29.673 E/VLC  ... (pts_delay increased to 5593 ms)
```
- 间隔 **7.78s / 7.70s**，几乎等距 → 不是随机网络抖动
- 每轮跟着一条 `decoder: output` → **解码输出被重建** → 用户看到的"顿住 + 黑一下"
- `pts_delay` **单调爬升** 1000 → 4692 → 5593 ms

### 11.2 已排除（都有依据，不是"感觉不像"）

| 嫌疑 | 依据 |
|---|---|
| 我们的卡顿看门狗 | `STALL_FROZEN_MS = 16000`，位置 16 秒不动才动作；日志无 `frozen=`；16s ≠ 7.7s |
| 网络缓存太小 | `prepare()` 用 `addOption(":network-caching=$bufferMs")` **覆盖**实例级 800；`BUFFER_MS` 默认 **5000ms**，实际缓存已是 5 秒 |
| OSD 显隐导致 Surface 重建 | 视频容器 `match_parent` 固定尺寸，OSD 是同级覆盖层（另一个 FrameLayout），不参与视频容器测量；`surfaceChanged` 是**空实现**，布局变化不会重挂 |
| 解码跟不上 / 热限频 | `com.litv.tv` CPU **19%**（800% 容量），温度 34–39°C，CPU 1804/2016MHz 未压频 |
| 本轮删的两行时钟参数 | 用户确认改前也一样卡；且改前那两行是存在的 → 不是变量 |

### 11.3 新线索：屏幕跑在 120Hz

```
mActiveSfDisplayMode = DisplayMode{id=1, refreshRate=120.00001}
mDefaultPeakRefreshRate: 60.0
supportedModes: 60 / 90 / 120
PRIORITY_MIUI_REFRESH_RATE -> Vote{maxRefreshRate=120.0}
```
MIUI 可变刷新率机型在视频场景会在 60↔120 间切模式，每次切换都可能闪一帧。
**但它解释不了 `ES_OUT_SET_PCR too late`**（那是输入侧报错），所以可能是**两个独立问题叠加**。

### 11.4 结论：分两条部署路径，别混

⚠️ **这一节第一版写错过，已更正。** 第一版把"服务端 `manifest_cache.go` 持锁回源 850ms"
当成根因 —— 那只对 **NAS 中转（relay）** 部署成立。实际用户用的是 **edge + direct**，
那条路上服务端不转发任何字节，所以那个结论对他无效。

| 部署路径 | 清单由谁取 | 850ms 归谁 | 可用的修法 |
|---|---|---|---|
| **NAS 中转**（`mode=relay`，`/live/{id}/remux.m3u8` 等） | 服务端 `liveManifest`，缓存 2s，过期后**持 `slot.mu` 同步回源** | **我们**（`manifest_cache.go`） | 服务端改 stale-while-revalidate；客户端零改动 |
| **edge + direct**（`mode=direct`，见 `edge/src/index.ts:626-637`） | **客户端直接连上游源站** | **上游源站**，我们改不了 | 只能客户端侧调参 / 选型（见 11.5） |

`edge/src/index.ts` 的原话：`mode: "direct"`、`url: row.url`、注释「服务端不转发任何字节」。
edge 只做解析 m3u、选题、下发表单三件事。

**仍然成立的通用证据**（与部署路径无关）：

| 证据 | 说明 |
|---|---|
| `ExoEngine: 加载慢 847ms / 1KB（-1）`，150 秒内 19 次，间隔 ~7–8 秒 | `trackType = -1` = `TRACK_TYPE_UNKNOWN` = **HLS 清单本身**；1KB 正是一份 m3u8。分片（`trackType` 为数字）**一次都没慢过** |
| VLC 侧 `ES_OUT_SET_PCR ... too late`（pts_delay 1000→4692→5593）×3 | VLC 播的也是同一份 m3u8，同样每轮被饿一下；它的应对是"加大延迟 + 重建输出"，Exo 的应对是"重缓冲" |
| `play.log` 有 `ERROR_CODE_BEHIND_LIVE_WINDOW` + "seek 回直播边缘" | 直播延迟 > 源站窗口 |
| **引擎无关性（实测）**：同一台在 Exo 下 141 秒内 `加载慢` 9 次（825–953ms）、`位置回落` 12 次、`BEHIND_LIVE_WINDOW` 2 次；在 VLC 下是 `pts_delay` 爬升 + 重建输出 | 换内核不改变症状 → 病因不在任何单一内核里 |

**两个引擎症状不同、病因同一个**：HLS 清单重载期间喂不上数据。
**且这条对 edge 部署同样成立** —— 慢的是源站的 m3u8，不是我们的服务。

### 11.5 修复方案（按部署路径分开）

**A. edge + direct（当前部署）—— 只能客户端侧调参，两个都能在 App 设置里直接试**

| 动作 | 位置 | 期望 |
|---|---|---|
| 直播延迟 `8000 → 2000` | 设置 → 直播延迟（选项 2000/4000/6000/8000/10000） | 若源站窗口比 8 秒还短，这一步直接消掉 `BEHIND_LIVE_WINDOW` |
| 缓冲 `5000 → 8000` | 设置 → 缓冲（选项 1000…8000） | 让 850ms 的清单缺口吃不穿缓冲 |

> 这两项**不用改代码、不用重装**，改完重新起播即生效。
> 若两项都调完仍卡，再考虑：优先选非 HLS（`.ts`）线路 —— 渐进式 TS 没有清单重载，
> 从机制上就不存在这个问题。这需要改"多线路择优"的排序（客户端侧）。

**B. NAS 中转 —— 服务端根治**

`liveManifest` 过期时**先返回旧快照**、后台刷新（stale-while-revalidate），
消掉持锁回源那 850ms。风险：清单可能旧 2–6 秒，须限制最大陈旧度，
否则上游已删的分片会 404。

**C. 两条路径都适用**：把 `LIVE_OFFSET_MS` 的默认值从 8000 降下来，
或改成"按 `PlayInfo` 下发的窗口长度 clamp"（窗口未知时取保守值）。
现在默认 8000 是**没有依据**的：源站窗口我们根本不知道，8 秒对短窗口源必然越界。


### 11.7 源站实测（2026-11-17 03:0x，PC 侧直连）

对 `cctv1-MCP`（`group-title="央视-MCP"`，30 个台的统一形态）实测：

| 项 | 实测值 |
|---|---|
| 取清单 `time_starttransfer` | **1.64 / 1.17 / 1.30 / 1.55 / 1.51 s**（连续 5 次，无一次快） |
| `time_total - tst` | ≈1 ms → **全部耗在服务端**，非带宽 |
| 30 条背靠背请求 | **503 × 21**；改成每条间隔 1 秒后 **200 × 30** → **源站会限流** |
| `#EXT-X-TARGETDURATION` | 7（另一次快照 8） |
| 分片数 / 窗口 | **3 条 / 15.56 s**（另一快照 3 条 / 19.32 s） |
| `#EXTINF` | 4.520 / 4.680 / **6.360**（时长不齐） |
| `#EXT-X-DISCONTINUITY` | **无** |

播放器只能自己去修这个错，每次修就是一次 seek/刷新。

### 11.8 手机侧日志的对应关系（这是最后一层证据）

| 现象 | 数量 | 说明 |
|---|---|---|
| `位置回落 …（HLS 重载，正常）` | **每 ~8 秒一次**（335 秒里 40 次） | 时间轴被修正 → 内部 seek → 解码刷新 |
| `重缓冲：播放中回到 BUFFERING` | **335 秒里只有 1 次** | **不是数据断供** |
| 两者时间关系 | **全库 0 对在 2 秒内**（最近一次差 5.2 秒） | 说明顿的那一下**不是重缓冲**，是时间轴修正 |
| `加载失败` / `5xx` | 播放链路 **0 次**（唯一一次是 VLC 解码错误换内核） | 手机侧**没有**撞上源站限流 |

**所以最符合全部证据的解释**：卡顿不是"数据不够"，而是**每 ~8 秒一次的时间轴修正**——
源站的 PDT 与真实分片时长不一致，播放器每个分片边界都要重对时间轴、刷新解码，
表现为「画面顿一下」，而音频通路不受影响（与用户观察一致：**UI 顺畅、只有画面顿**）。

> 状态：这是**假设**，还差一步确认 —— 让用户记下"看到卡顿"的墙钟时间，
> 与 `位置回落` 的时间戳对齐。若吻合即实锤；若不符则推翻，回到 11.4。

### 11.9 客户端还能做什么（诚实的边界）

- 缓冲**已经到头**：`minBuffer = 缓冲设置(8s)`、`maxBuffer = 4×` 上限 40s，
  而源窗口本身只有 15.5 s —— 再大也囤不下。**加缓冲解决不了这个问题**。
- 唯一可能有效的客户端手段是**忽略 `#EXT-X-PROGRAM-DATE-TIME`**，但 Media3 的
  `HlsPlaylistParser` 没有暴露这个开关，要自己改解析器或换内核 —— 代价大、风险高。
- 现实可行的只有：**换同台的其它线路 / 换源**。这条源（`*.mcp.*` 这类 MCP 转流）
  在清单层面的质量就是不达标的。

### 11.10 这次排查里踩到的坑（方法论）

- **别把 `findstr` 用来匹配中文**：它对 UTF-8 中文静默失败，会把"有"报成 0 命中。
  正控（拿一条确定存在的中文日志去试）必须先做。
- **`TRACK_TYPE_UNKNOWN` 就是清单**：`onLoadCompleted` 里 `mediaLoadData.trackType`
  为 `-1` 时量的是 m3u8，不是分片。这一条直接把"慢在哪"定位到了清单。
- **`位置回落（HLS 重载，正常）` 那句注释误导了排查**：它把可观测现象标成"正常"，
  而用户能感知的卡顿正好发生在这个节奏上。注释不该替现象下结论。

## 12. 息屏/开屏后 VLC 黑屏（已修，2026-11-17）

**症状**：VLC 内核下，息屏再开屏 → **有声音、没画面（黑屏）**。Exo 不受影响。

**根因**（`VlcEngine.attach()`）：

```kotlin
if (mp.vlcVout.areViewsAttached()) {
    if (surface === attachedSurface) return   // ← 短路
    runCatching { mp.vlcVout.detachViews() }
}
```

这句短路是为了防"重复 `setVideoSurface` 把 vout 搞坏"（历史上真机出过撕裂/冻住）。
但息屏唤醒时 **SurfaceView 的 Surface 对象还是同一个**、`isValid` 也还是 `true`，
而**底层缓冲区已被系统回收** —— 短路成立、什么都不做，vout 继续挂着那个死 Surface。

而本来能救这种情况的 `resyncWindow()` 在 `vlcLayout != null` 时**提前 return**
（`PlayerManager.kt:434`，理由是"官方 helper 自己处理布局变化"），
可我们的电视/手机布局里恰好都有 `vlcLayout` → 这条路永远走不到。

**修法**（不重建播放器、不断流）：

| 位置 | 改动 |
|---|---|
| `VlcEngine.rebindVideo()` | 新增。刻意**不去重**：`detachViews → setVideoSurface → attachViews → scaleFor`，成功后 `syncWindowSize`，再用 `pause/play` 轻推唤醒出帧 |
| `PlayerManager.onHostResumed(awayMs)` | 新增。判定 + 兜底收在一处：重绑失败就退化为 `retryNow()` 重建（约 1 秒，总比永久黑屏好） |
| `WakeRebindPolicy` | 新增，**纯函数可单测**：`engine==vlc` 且（**真的息过屏** 或 `awayMs ≥ 1500`）才重绑 |
| `PlayerManager` 内的 `ACTION_SCREEN_OFF` 接收器 | 新增。**光看"离开时长"会漏掉最常见的情况**：用户快速按两下电源键（隔 1 秒），时长不到阈值，但 Surface 照样被回收。息屏广播是硬证据，读到即清（只影响这一次回前台） |
| `PlayerActivity.onResume` / `PhonePlayerActivity.onResume` | 取 `awayMs`（必须在清零 `pausedAtMs` 之前），调 `player.onHostResumed(awayMs)` |

**为什么要阈值**：不加 1500ms 门槛，弹个对话框、拉一下通知栏回来也会重绑，画面会闪一下。

**为什么还要 ACTION_SCREEN_OFF**：只有时长判据会漏掉"快速息屏再开屏"——
间隔 1 秒左右、时长不到阈值，但 Surface 一样被 `force-disconnect`。
息屏是硬证据，命中就重绑，不再看时长。

**未验证**：本地只做了编译 + 单测（`WakeRebindPolicyTest` 5 条）；
真机"息屏 30 秒 → 开屏"是否真的恢复画面**还没测**。

### 12.1 真机验证（2026-11-17 03:20，部分通过）

**结论：恢复成功，但走的不是"重绑"，是它的兜底"重建"。**

实测日志（`-s <device-ip>:<port>`，息屏 223 → 30s → 开屏 224 → 解锁 82）：

```

03:20:35.59 E/BufferQueueProducer: cancelBuffer: BufferQueue has been abandoned
03:20:35.68 E/VLC: libvlc gl: cannot create EGL window surface
03:20:36.71 I/PlayerManager: 回到前台：重绑 vout=false（离开 1610ms）

```
截图对比：息屏前与开屏后**都是正常画面**（CCTV1），不是黑屏、不是锁屏。

**必须说清的两件事**：

1. **`vout=false` 说明 `rebindVideo()` 在第一道 guard 就返回了**（`videoSurface == null`）——
   开屏瞬间 Surface 被 `force-disconnect` + `abandoned`，根本没有 Surface 可绑。
   真正救回来的是 `retryNow()` 重建。

| 情况 | `videoSurface` | 处理 | 验证 |
|---|---|---|---|

| Surface 对象还在、底层缓冲区已死（`attach()` 短路那种） | 非 null、`isValid=true` | **重绑** | ❌ **未复现，未验证** |

第二种才是 `attach()` 短路真正坑人的场景，也最可能对应"开屏是黑的"。本次没跑到，
因为解锁后 Surface 直接重建了 → 走的是 Rebuild 分支。

**副作用（记录，未处理）**：重建那一下主线程阻塞 1.7 秒
（`Choreographer: Skipped 207 frames, Davey! duration=1735ms`）。

**诊断改进**：`rebindVideo()` 的三处提前返回现在都打原因
（没有播放器 / `videoSurface` 为 null / Surface 无效），下次日志能直接看出走了哪条。

### 12.2 第二版修错了，真机把画面修成黑屏（2026-11-17 03:30）

**快速息屏（按两下电源键，间隔约 1 秒）时**：识别正确（`息屏=true` 生效），
`rebindVideo` 也进去了，但 `videoSurface` 已是 null → 退回 `retryNow()` 重建 →
**重建出来的播放器没有视频输出**：

```
03:30:21.027 destroy c2.qti.avc.decoder          ← 解码器被销毁
03:30:23.404 rebindVideo: 跳过，videoSurface 已为 null（Surface 被销毁）
03:30:23.404 回到前台：重绑 vout=false（离开 2451ms，息屏=true）
03:30:23.404 回到前台：重绑失败，改为重建播放
03:30:23.549 attachViews ok 2624x1172
03:30:23.550 VLC play() 已调用
                                                 ← 之后再无 create c2，render buffer PTS 0 条
```
截图实测：**平均亮度 1.5（满 255）、只有 3 种颜色 = 纯黑**。

**根因（我的代码，不是 VLC）**：`VlcEngine.prepare()` 里挂 vout 那段是

```kotlin
videoSurface?.takeIf { it.isValid }?.let { ... setVideoSurface / attachViews ... }
```

Surface 为 null 时**整段跳过** → 播放器起来时没有视频输出。
所以"没有 Surface 就重建"必然产生一个「有音频、没画面、且不会自愈」的状态。

**为什么第一次（12.1）看起来是对的**：那次 Surface 已被系统重建好
（`surfaceCreated` 先触发），重建时拿得到 Surface，所以成功了。
**换一个时序就崩 —— 这属于验得不到位，不是 VLC 的问题。**

**第三版修法**：

| 改动 | 说明 |
|---|---|
| `PlayerManager.onHostResumed()` 增加 Surface 守卫 | `surface == null \|\| !isValid` 时**不重建**，只置 `pendingStartForSurface = true` 挂起，等 `attach()` 把 Surface 交过来再 `startCurrent(force = true)` |
| `PlayerActivity.onResume()` 交两次 Surface | 立刻一次 + 600ms 后再补一次。防「`surfaceCreated` 晚于 onResume 或干脆不回调」→ 挂起变永久黑屏 |

> 状态：**第三版已编译、未完成真机复测**。
> 教训记在这里：把"某一个时序下能恢复"当成"修好了"，代价是把用户画面弄黑。

## 13. VLC 画面只占容器 56.25%（手机首页预览框）

**症状**：手机界面上 VLC 播出的画面明显偏小，看起来"没按比例 / 没铺满"。

**量化**（1220×2712 截图，PIL 像素级）：

| 项 | 值 |
|---|---|
| 容器（纯黑矩形） | **1220 × 686**（与日志 `VLCVideoLayout 1220x686` 一致） |
| 视频内容 bbox | **686 × 386**，宽高比 **1.777 ≈ 16:9** |
| 占容器 | 宽 **56.23%**、高 **56.27%** ≈ **9/16** |
| 位置 | 水平居中（左右各 267）、垂直居中（上下各 150） |

**关键推理**：**比例是对的**（16:9），只是整体被缩小到容器的 9/16。
686 正好等于容器**高度** → 说明 libVLC 认为窗口是 **686×686**（方形），
于是把 16:9 内容缩成 686×386 再居中。

**根因**：`syncWindowSize()` 是 `post` 出去的，执行时 `VLCVideoLayout`
只量出了高度、宽度还是旧值（=高度），于是 `setWindowSize(686, 686)`。
而 **vout 挂上之后，事后改窗口尺寸 libVLC 不会重新布局**
（`PlayerManager.resyncWindow()` 的注释早就写过"VLC 不接受事后改窗口尺寸"）。

**修法**：

| 改动 | 说明 |
|---|---|
| 新增 `applyWindowSizeNow()` | **同步**设置窗口尺寸，且在 `attachViews` **之前**调用（两处挂载点都插了） |
| 宽度兜底 | 若 `vlay.width` 没量完（等于高度），借**父容器宽度**（1220） |
| `syncWindowSize()` 改用 `vlcLayout` | 原来用 `hostView`（`android.R.id.content` = 整屏），VLC 按整屏算内层 |
| `scheduleRefit()` | attach 后 0/250/700/1500ms 各压一次内层为 MATCH_PARENT（防 libvlc 回写） |

**顺带修的另一个 bug**：`scaleFor()` 原来把 `auto`（以及未知值）映射成
`SURFACE_FILL`（拉伸填满），而注释写的是"保持原始比例"——注释与代码相反。
已收敛到 `AspectPolicy`（带 5 条单测）：**只有显式「铺满」才 FILL**。

> 验证状态：单测 86/86 绿；**真机 bbox 是否变成 ≈1220×686 待最后一轮实测**。

### 13.1 实测推翻"窗口尺寸"假设（2026-11-17 04:08）

改前那版（`syncWindowSize` 已改用 `vlcLayout`、`scheduleRefit` 已上）的完整日志：

```

tree   player_surface_frame 1220x686
tree     surface_video 1220x686        ← View 层全部正确
refit@0ms / @250ms / @700ms / @1500ms：1220x686
已设置 VLC 窗口尺寸 1220x686  ×4        ← 窗口尺寸也确实传对了
```
但截图里视频仍然是 **686×386**（占容器 56.23%）。

**结论：窗口尺寸不是原因，我上一条的推断是错的。**
View 层 1220×686、`setWindowSize` 也传了 1220×686，
libVLC 仍然把 16:9 内容按 **9/16 = 0.5625** 的因子缩小后居中画出来。

剩下的可能（都还没验证）：

1. `videoScale` / `aspectRatio` 与 vout 的交互：`SURFACE_BEST_FIT` 在 libVLC 3.5.1 上
   对"窗口已知但视频尺寸未知"的组合可能退化成按某个基准缩放
2. vout 创建时机早于 `setWindowSize`（虽然日志顺序看似正确）
3. 走**不用 VLCVideoLayout** 的路径（直接 `setVideoSurface` + `AspectRatioFrameLayout`）——
   这也是电视端 `resyncWindow()` 里那条"重建一次"的路，但代价是重建
4. 换 Exo 播这个预览框（Exo 的 `AspectRatioFrameLayout` 行为可预期）

> 教训（第三次同类）：**"把参数设对了"不等于"行为对了"**。
> 这次 View 尺寸和 window size 全对，画面还是小 —— 说明真正的缩放因子在
> libVLC 内部，光看我们自己的代码推不出来。下一轮应该先用
> `--vout=...`/`--verbose=2` 打开 librtcp 的 vout 日志看它算出的 rect。

### 13.2 真正的根因：`getIdentifier` 用错包名，压尺寸的代码从没执行过

`stretchInnerSurface()` 里找内层 View 用的是：

```kotlin
res.getIdentifier(name, "id", "org.videolan.libvlc")   // ← 恒为 0
if (id == 0) continue                                  // ← 整段跳过
```

项目开了 `nonTransitiveRClass=true`，VLC 的资源 id 被合并进**应用自己的包**，
用库包名查必然返回 0。所以「把内层压成 MATCH_PARENT」**从来没有生效过**
（真机日志里一条 `内层 … 已设为铺满` 都没有）。之前看到的 1220×686 是
libVLC 自己初始算的，不是我们压的。

改成**遍历视图树按资源条目名匹配**后，日志立刻变成：

```
内层命中 3 个：[2131362316, 2131362448, 2131362447]
内层 … 已设为铺满 ×15
内层 2131362448 被缩到 686x389，压回 1220x686（第 1/20 次）
```

**但仍然没解决**：`player_surface_frame` 被撑满了，`surface_video` 依旧被
libVLC 在下一帧写回 686×386，只是从"居中"变成"贴左上"
（`displayFrame` 从 `[267 394 953 780]` 变成 `[0 244 686 630]`）。
**只要用 `VLCVideoLayout`，内层尺寸就归 libVLC 管，改不动。**

### 13.3 最终修法：手机首页预览框不再用 VLCVideoLayout ✅ 已验证

`PhoneHomeActivity.onEngineChanged()` / `onResume()` 两处改成：

```kotlin
findViewById<View>(R.id.surface).visibility = VISIBLE      // VLC 也用普通 SurfaceView
findViewById<VLCVideoLayout>(R.id.vlcLayout).visibility = GONE
player.setVlcLayout(null)                                   // 让 VLC 走 setVideoSurface
```

这样首页预览框和**全屏播放页走完全相同的路径**
（`activity_phone_player.xml` 里本来就只有普通 SurfaceView），
VLC 不再接管内层尺寸，SurfaceView 是 match_parent 的 1220×686。

**真机验证（2026-11-17 04:30，两种独立方法一致）**：

| 项 | 修前 | 修后 |
|---|---|---|
| `displayFrame` | `[267 394 953 780]` = 686×386 | **`[0 244 1220 930]` = 1220×686** |
| 内容宽 / 容器宽 | 56.23% | **99.92%** |
| 四边黑边 | 267 / 267 / 150 / 150 | **0 ~ 1 px** |
| `sourceCrop` | `[0,0,1920,1080]` | `[0,0,1220,686]` |
| 日志 `内层命中` | 0（改遍历后为 5 次） | **0（不再走 layout 分支）** |
| 在播 | — | 帧间 99.68% 像素变化 |

> **电视端也已改成同样结构**（2026-11-17，`PlayerActivity` 的 `onEngineChanged` 与
> `surfaceCreated` 统一 `player.attachVideoLayout(null)`，`vlcLayout` 恒 GONE）。
> 至此**全项目没有任何地方再把 `VLCVideoLayout` 交给引擎**，
> libVLC 的内层尺寸计算彻底不参与。
>
> 但 TV 上的 VLC 路径**没有真机验证**：那台电视之前一直选的是 Exo
> （`VlcEngine = 0`），要验得先在电视上把「播放内核」切成 vlc 再播。
> 若发现电视上 VLC 画面异常，回滚点就是 `PlayerActivity.onEngineChanged` 里那三行。

## 14. 切全屏 / 旋转：卡顿、裁切、冻结（2026-11-17 05:00–05:40）

**症状**：手机切换全屏/竖屏时画面卡一下。

### 14.1 卡顿的来源：`resyncWindow()` 在重建整条播放

```kotlin
fun resyncWindow() {
    ...
    main.postDelayed({ Log.i(TAG, "resync: 用新尺寸重建 VLC"); retryNow() }, 400)
}
```
`retryNow()` 等价换台重连（约 1 秒黑屏）→ 每次切屏都顿一下。

### 14.2 试过"原地重挂"，结果是**冻结**（已回滚）

新增的 `reattachVideo()`（detach → setVideoSurface → attachViews → pause/play 轻推）
确实去掉了那 1 秒，日志也打 `reattachVideo: ok=true` / `resync: 原地重挂成功（不重建）`。

但真机结果是**回竖屏后画面冻结**：像素变化 0.00%（横屏期间 44.6%），
音频照常、`ok=true`。这正是代码里原本就写着的那句
「attach 成功但视频输出已死、pause/play 唤不回」。
**冻结比卡 1 秒更糟**，所以 `resyncWindow()` 已回滚成重建；
`reattachVideo()` 只留给"息屏唤醒"用（那条路已验证有效，且失败会自动退化到重建）。

> 教训：`ok=true` 只表示**调用没抛异常**，不代表几何对、更不代表在出帧。
> 验收必须看**像素是否在变** + `displayFrame` 是否合理，不能看返回值和日志措辞。

**回滚后的真机验证（2026-11-17 05:29，两轮独立复现）**：

| 阶段 | 视频区像素变化率（4s） | 容器高度 = SF 层高度 | 内容占容器宽 |
|---|---|---|---|
| 竖屏基线 | 91.85% | 686 = 686 | 99.92% |
| 横屏 | 93.58%（复采 96.05%） | 686 = 686（dH=0） | 100% |
| **回竖屏 P1→P2** | **96.83%** | 686 = 686 | 99.92% |
| 回竖屏 P2→P3（10.8s） | **96.06%** | — | — |

对照组：同一对截图的标题栏 / 节目单区域变化 **0.00%** → 96% 确实是画面在动。
日志：`resync: 用新尺寸重建 VLC` + `VLC play()`，`reattachVideo` 0 次 —— 走的是重建路径。
**冻结未复现，裁切未复现。**

### 14.3 修好的部分：横屏裁切

横屏时 `applyVideoRatio()` 用 `parent.height`（932）算 16:9 高度，而 `LinearLayout`
只给 box 854 → 里面的 `AspectRatioFrameLayout` 仍量成 932 → **底部 78px 溢出，
被底部 tab 栏盖住（字幕被从中间切断）**。

修法：可用高度扣掉同容器里**其它可见子项**（顶部标题栏等）：
```kotlin
val siblingsH = (parent as? ViewGroup)?.children
    ?.filter { it !== box && it.visibility == VISIBLE }?.sumOf { it.height } ?: 0
val usableH = (availH - siblingsH).coerceAtLeast(1)
```
验证：两个方向的 `SurfaceView` 层高度都**严格等于** `videoBox` 高度
（686 = 686，上一轮 932 vs 854），画面最后一行 y=929 仍是画面、930 起是背景。

**顺带修的方向 bug**：`landscape` 是缓存字段，只在 App 自己的全屏按钮里翻转，
系统旋转时不更新 → `applyVideoRatio()` 走竖屏分支，横屏容器变成 2624×686。
现在改成从 `Configuration.orientation` 取，并等父容器**真的换过尺寸**再算
（`addOnLayoutChangeListener` 一次性监听 + 200ms 兜底）。

### 14.4 已知取舍：横屏不铺满

现在横屏容器 = `usableH(932−246) × 16:9` ≈ **1219×686**，比例正确、不裁切，
但 2712 宽的屏幕上左右各留约 700px 黑边 —— **横屏没有铺满**。
要铺满得让视频区在横屏时隐藏「正在播」信息行 / 底部 tab（即真正的全屏模式），
属于布局决策，本轮没做。
