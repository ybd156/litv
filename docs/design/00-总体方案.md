# LITV — IPTV 多终端管理平台 · 总体方案

> 版本 v0.1（决策稿） · 2026-11-01
> 本文是**决策文档**：先给结论，再给选项与代价。带 ⭐ 的是我的推荐。
> 合规前提：本项目是**中立的源管理与播放外壳**，不提供、不预装、不分发任何直播源/EPG/内容；源由用户自行导入并自负合规责任。产品文档、安装向导、README 均需保留此声明。

---

## 0. 一句话定位

部署在飞牛 NAS 上的「**直播源 + 频道编排 + 多终端分发**」中台：
- **服务端**：单个 Go 静态二进制，打成 fnOS 原生 `.fpk`，无 Docker、无外部依赖；
- **管理台**：走飞牛统一网关，**点开即登录**（网关注入 `X-Trim-Userid`）；
- **终端**：Android TV / Android 手机 / iPhone 三端原生 App，绑定码接入，播放内核 **Media3 + libmpv 双引擎**。

## 2. 总体架构

```
                        ┌──────────────────────── 飞牛 NAS (N100) ────────────────────────┐
                        │                                                                  │
  浏览器(飞牛桌面)        │  fnOS 统一网关 (nginx)                                            │
  ─── 点开应用 ─────────▶│    ├─ 校验 NAS 登录态                                             │
                        │    ├─ 注入 X-Trim-Userid / Username / Isadmin                     │
                        │    └─ 转发 → unix:${TRIM_APPDEST}/app.sock                        │
                        │                    │                                             │
                        │                    ▼                                             │
                        │        ┌──────────────────────────┐        ┌──────────────┐      │
                        │        │  litvd (Go 单二进制)      │◀──────▶│  SQLite      │      │
                        │        │  ├ /app/litv/*  管理台API │        │  (WAL)       │      │
                        │        │  ├ /app/litv/ws 实时推送  │        └──────────────┘      │
  电视 / 手机 / iPhone   │        │  ├ :28027 终端 API (TCP)   │        ┌──────────────┐      │
  ─── 绑定码 → token ───▶│        │  ├ /live/*  流出口        │◀──────▶│  EPG 缓存     │      │
                        │        │  └ /vod/*   点播出口      │        └──────────────┘      │
                        │        └──────────┬───────────────┘                              │
                        │                   │ 上游拉流 (HTTP-HLS / MPEG-TS / UDP组播 / RTSP)│
                        └───────────────────┼──────────────────────────────────────────────┘
                                            ▼
                                    互联网 / 运营商直播源（用户自行导入）
```

**三个入口，三套鉴权，互不污染**：

| 入口 | 谁用 | 鉴权 | 传输 |
|---|---|---|---|
| `/app/litv/*` | 管理台（浏览器） | fnOS 网关注入 Header | Unix Socket |
| `:28027/api/*` | 三端 App | 设备 token（绑定码换取） | TCP + TLS 可选 |
| `/live/*` `/vod/*` | 播放器 | 短期签名 URL（HMAC + 过期） | HTTP 流式 |

> 为什么要两个口？因为**网关只覆盖浏览器会话**——Android/iOS 原生 App 不会带飞牛的 Cookie。这是架构级分叉点，见 §11 问题 1。

## 3. 服务端技术选型（请拍板）

### 3.1 语言 / 框架

| 选项 | 优势 | 代价 | 结论 |
|---|---|---|---|
| ⭐ **Go + chi/gin** | 单静态二进制（~15MB）、交叉编译零痛苦、goroutine 天生适合「1 路源分发 N 个客户端」、内存占用低（N100 友好）、ffmpeg 子进程管理简单 | 泛型/生态不如 Node 花哨 | **推荐** |
| Node + TypeScript | 前后端同语言、生态最全、开发最快 | 需打包成 SEA/pkg 才有单文件；长连接+多路流内存抖动大；N100 上更吃资源 | 备选 |
| Python + FastAPI | 原型最快、ffmpeg/解析生态好 | 单文件分发要靠 PyInstaller（体积 50MB+、启动慢）、GIL 限制高并发流 | 不推荐 |
| Rust + axum | 性能/内存最优 | 开发速度慢 3~5 倍，本项目 UI 逻辑多，不划算 | 不推荐 |

**理由**：这个产品的瓶颈不在 CPU 而在于「大量并发 IO + 低内存 + 单文件部署到 NAS」，Go 是唯一同时满足三者的。

### 3.2 数据库

| 选项 | 适用 | 结论 |
|---|---|---|
| ⭐ **SQLite (WAL)** | 单机 NAS、零运维、备份=拷一个文件 | **推荐**（默认） |
| PostgreSQL | 多用户高并发、要与飞牛系统库共存 | 仅当你要多实例/多租户 |
| MySQL/MariaDB | 飞牛生态有 MariaDB fpk 可依赖 | 增加 `install_dep_apps` 耦合，不划算 |

**设计**：所有 DB 访问走一层 `store` 接口，SQLite 为默认实现，未来换 PG 只改实现。EPG 这种大表用**独立 SQLite 文件 + 按天分片**，避免拖慢主库。

### 3.3 管理台前端

| 选项 | 优势 | 代价 |
|---|---|---|
| ⭐ **Vue 3 + Vite + Naive UI** | 中文生态最好、组件全、体积小（~200KB gzip）、`base: '/app/litv/'` 一行搞定子路径 | — |
| React + Ant Design | 组件最丰富 | 体积大（~500KB+），子路径部署要改 router basename |
| Go 模板 + HTMX | 零构建、单二进制内嵌 | 复杂表格/拖拽排序难写，管理台交互重，会很难受 |

**关键坑**：网关模式下前端必须以 `/app/litv/` 为 base 构建，且**结尾带斜杠**，否则白屏/404（社区翻车最多的地方）。Vite 里 `base: '/app/litv/'`，路由用 hash 模式最稳。

## 4. 飞牛账号接入（已查证，官方唯一正路）

### 4.1 机制（官方文档确证）

`app/ui/config` 注册 `gatewayPrefix` + `gatewaySocket` → 用户访问 `/app/litv` → 网关**先校验 NAS 登录态**再转发到你的 Unix Socket，请求头带：

| Header | 含义 |
|---|---|
| `X-Trim-Userid` | 当前用户 UID |
| `X-Trim-Username` | 用户名 |
| `X-Trim-Isadmin` | 是否管理员 |

官方定性：**可作为可信身份上下文**，但应用仍需自己做业务鉴权；并明确警告「不要信任客户端传入的用户 ID，只用网关 Header」。

→ 这就是「点开应用即已登录」，不用破解任何东西。

### 4.2 落地做法（方案 A + B 组合）

- **A｜管理台免登录**：中间件读三个 Header，首次见到 uid 时 upsert 到 `users(uid, username, is_admin, first_seen)`。`is_admin` 只放行系统级操作（改端口、删源、看日志）。业务权限（谁能看哪些分组）用自建表。
- **B｜终端绑定码**：电视/手机首次启动显示 6 位码 → 管理台确认 → 换长期 `device_token`。终端不参与 SSO。
- ❌ **不做 C（OIDC 桥接）**：社区项目 `fnos-oidc-bridge` 能反向工程飞牛内部 OAuth，但要 root、要写 fnOS 的 PostgreSQL `trim.oauth_app` 表、随系统升级可能失效，且上架审核不友好。我们只需要「自己应用免登录」，A 已满足。

### 4.3 fpk 打包规范（已从官方文档 + 真实生产包双向确认）

```
package/
├── manifest              # key=value 文本（不是 YAML）
├── ICON.PNG / ICON_256.PNG
├── cmd/
│   ├── main              # ★ 唯一入口：start|stop|restart|status
│   ├── install_init / install_callback
│   ├── config_init  / config_callback
│   ├── upgrade_init / upgrade_callback
│   └── uninstall_init / uninstall_callback
├── config/
│   ├── privilege         # 运行身份 + join-groups（QSV 硬解用 video,render）
│   └── resource          # data-share / api-scope
├── wizard/               # 安装向导（JSON：text/password/radio/tips）
│   ├── install / config / uninstall
├── i18n/zh-CN, en-US ... # ${common.displayName} 等变量来源
└── app/                  # 应用负载（会被打成 app.tgz）
    ├── server/litvd_x86_64
    ├── www/              # 管理台静态文件
    └── ui/config         # 网关入口注册
```

**与 Linux 直觉不同的三点（必踩）**：
1. **没有 systemd/supervisor**。飞牛直接调 `cmd/main start|stop|status`，靠**退出码**判活（0 运行 / 3 未运行 / 1 失败）。PID 文件、崩溃拉起、日志轮转全要自己写。
2. **目录全用环境变量**：`TRIM_APPDEST`(程序) / `TRIM_PKGETC`(配置) / `TRIM_PKGVAR`(持久数据) / `TRIM_PKGTMP`。物理位置在 `/vol{n}/@appdata/litv`，经 `/var/apps/litv/var` 软链。没有官方日志目录，惯例写 `$TRIM_PKGVAR/litv.log`。
3. **默认非 root**（`run-as: package`）。要 QSV 硬解就加 `"join-groups": ["video","render"]`，**不要为了硬解开 root**。

**打包**：用官方 `fnpack`（已验证 1.0.4 可下载可用），`fnpack build --directory package`。`.fpk` 实质是 tar.gz，负载在 `app.tgz`，`manifest.checksum = md5(app.tgz)`。

## 5. 服务端模块划分

| 模块 | 职责 | 关键实现点 |
|---|---|---|
| `source` | 订阅源拉取与解析 | 支持 **M3U/M3U8**、**TXT**(`分组,#genre#` + `名称,url`)、**TVBox lives JSON**；自动识别 GBK/UTF-8/BOM；去重（URL 归一化 + 名称相似度） |
| `channel` | 频道编排 | 分组、拖拽排序、台标抓取与本地缓存、多线路（同一频道多个源 URL）、频道号 |
| `epg` | 电子节目单 | XMLTV 解析、按天缓存、`tvg-id` 缺失时用「名称 + 别名表」模糊匹配；对外提供 `/api/epg/{chid}?day=0` |
| `probe` | 源健康检查 | 后台低优先级并发探测（不打扰正在播的用户），记录码率/分辨率/编码/延迟，失效自动降权 |
| `stream` | 流出口（核心） | **上游连接复用**：同一频道 N 个客户端只拉 1 路上游；MPEG-TS 透传 + **连续性计数器修复**；UDP/RTP 组播接收（带 jitter buffer）；HLS 上游用 m3u8 重写代理 |
| `transcode` | 按需转码 | ffmpeg QSV（`h264_qsv`/`hevc_qsv`，`-tune zerolatency`），仅在「源编码终端解不了」时触发；默认关闭 |
| `device` | 终端管理 | 绑定码、device token、在线心跳、远程配置下发、OTA 分发 |
| `auth` | 鉴权 | 网关 Header 中间件 + 设备 token + 流 URL HMAC 签名 |
| `admin` | 管理台 | 内嵌静态文件（`go:embed`），SPA 兜底路由 |
| `ws` | 实时通道 | 终端在线状态、转码任务进度、日志尾巴推送 |

### 5.1 流出口设计（决定成败的部分）

```
GET /live/{sig}/{channel_id}.m3u8?token=...   # 终端只认这一个地址
   │
   ├─ 签名校验（HMAC-SHA256(channel_id + exp + device_id, secret)）
   ├─ 查 hub：该 channel 是否已有上游连接？
   │    ├─ 有 → 加入 fanout 组，直接读环形缓冲（快，切台 <300ms）
   │    └─ 无 → 建立上游，预填 2~3 个 GOP 到缓冲再放行
   └─ 输出：透传 TS（不转封装）或 HLS 切片
```

**要点**：一个频道只拉一路源、环形缓冲 + 新客户端从最近的 keyframe 起播，这是「毫秒级换台」和「家庭多终端省带宽」的关键。

## 7. 客户端设计（TV 性能是主战场）

> 详细的播放内核选型见 `docs/research/02-stack-and-oss.md`；本节给架构结论。

### 7.1 Android TV（优先做，性能要求最高）

**技术栈**：Kotlin + **Compose for TV**（新页面）/ Leanback 兼容层（老设备兜底），minSdk 21，targetSdk 34。

**性能预算（硬指标，逐条验收）**：

| 指标 | 目标 | 手段 |
|---|---|---|
| 冷启动到首屏 | < 1.5s | 无网络阻塞首屏、本地缓存上次频道列表、启动即预连接上次频道 |
| 切台时间 | < 1s（同源 <300ms） | 服务端 fanout + 客户端 `DefaultLoadControl` 调优 + 预建连接 |
| 频道列表滚动 | 60fps | RecyclerView/Compose LazyList + 台标 glide/coil 缩略图 + 分页 |
| 内存峰值 | < 200MB（1GB 盒子） | 单实例播放器、及时 release、图片 LRU 上限 |
| 遥控器响应 | < 50ms | 按键事件不排队、不阻塞主线程 |

**双内核策略**：
- **Media3/ExoPlayer 为默认**：硬解走 MediaCodec，起播快、功耗低、HLS 支持好；
- **libmpv 为兜底**：Media3 解不了的（AVS3/AVS2、异常 TS、特殊音频）自动降级到 libmpv 软解；
- 切换策略：解析探测（codec 白名单）→ 首选 Media3 → 起播超时/报错 → 3s 内自动切 libmpv，并把「该频道用哪个内核」记到本地，下次直接用对的。

### 7.2 Android 手机

同一 codebase，`res/layout-w600dp` + 触摸手势层：
- 竖屏：底部 Tab（直播/收藏/EPG/我的），播放页支持手势（左亮度/右音量/上下滑换台）；
- 横屏/平板：复用 TV 的列表+预览布局。

### 7.3 交互逻辑（TV 遥控器）—— 见 §8

### 7.4 iOS（xtool）—— 有硬约束，必须提前说清

**能做的**：xtool 可以在 Linux/WSL 上编译 Swift/SwiftUI 并产出 `.ipa`，链接系统框架（AVFoundation/AVPlayer）没问题。

**难点**：
1. **libmpv/FFmpeg 上 iOS 需要 iOS SDK 与 Apple 工具链**，交叉编译 mpv 依赖链（ffmpeg/libass/libplacebo/moltenvk）在 Linux 上极其痛苦；
2. 即使编出 `.a`，**签名安装**仍需 Apple ID（免费证书 7 天有效期）或 TrollStore/侧载工具；
3. 结论：**iOS 首版用 AVPlayer（系统原生解码）**，覆盖 HLS/TS + H.264/H.265 + AAC 的主流直播；遇到 AVS3/AC3 等再评估 VLCKit 或 MobileVLCKit。

> 这是我在动手前必须和你确认的点（§11 问题 4），因为它决定 iOS 端工作量是「2 周」还是「2 个月」。

## 8. UI / 交互逻辑（TV 优先，符合直觉）

设计原则：**老人小孩不看说明书也能用**。所有操作必须能用「方向键 + OK + 返回」完成。

| 场景 | 遥控器 | 触屏 |
|---|---|---|
| 呼出/关闭 OSD 信息条 | OK | 单击 |
| 呼出频道列表 | ← | 右滑 |
| 列表内浏览 / 换分组 | ↑↓ / ←→ | 上下滑 / 顶部 Tab |
| 选中播放 | OK | 点击 |
| 直接换台（无面板时） | ↑↓ | 上下滑 |
| 数字键直接跳台 | 0-9 | 数字键盘 |
| 呼出 EPG | 列表中 → | 左滑 |
| 设置栏 | Menu | 双击 |
| 线路/清晰度切换 | 长按 OK | 长按 |
| 音量 | 遥控器音量键 | 右侧上下滑 |
| 音轨/字幕 | INFO | OSD 按钮 |

**布局**（16:9 安全区，10% 边距）：
- 首页：顶部「正在播放」大卡 + 横向分组 + 频道网格（每行 6 个，台标 + 名称 + 当前节目）；
- 频道列表：左侧分组竖列 + 右侧频道列表（当前项高亮放大 1.05x + 焦点描边）；
- 播放页：底部 1/3 半透明渐变 OSD，显示频道名、EPG 当前/下一档、进度条、按钮组；
- 焦点态必须**双重视觉反馈**（放大 + 描边），不能只靠颜色。

## 10. 还能增加什么功能（按性价比排序）

**第一梯队（建议首版就做，成本低、体验提升大）**
1. **一键回看/时移**：录制最近 N 小时，配合 EPG 拖动回看（NAS 有硬盘，天然优势）。
2. **终端远程配置**：在管理台改解码模式/缓冲/画面比例，电视端下次心跳生效——不用跑去客厅按遥控器。
3. **多源自动择优**：同一频道挂多个源，探测延迟/码率后自动选最快，失败自动切。
4. **手机当遥控器**：手机 App 扫码连到电视端，直接当输入设备（免装第三方）。
5. **开机自启 + 断流重连**：老人机场景刚需。

**第二梯队（差异化）**
6. **EPG 智能匹配 + 手动纠错**：拖拽把频道拖到 EPG 频道上，一次配置永久生效。
7. **多用户观看隔离**：不同家庭成员不同分组/收藏（用 `X-Trim-Userid` 天然支持）。
8. **录制中心**：定时录制、EPG 一键录制、录制文件直接落到飞牛共享目录（`config/resource` 的 `data-share`）。
9. **观看统计**：哪个频道最常看、卡顿率、平均起播时间（指导你优化源）。
10. **客户端定制打包**：管理台一键生成「带自己台标/名称/默认服务器地址」的 APK（借鉴 mediaplayer 的做法）。

**第三梯队（锦上添花）**
11. **Web 端播放**（浏览器直接看，免装 App）。
12. **DLNA/投屏** 出口。
13. **源市场/订阅分享**（仅分享源的结构，不托管内容——注意合规）。
14. **告警通知**：源失效推送到飞牛通知/Telegram。
15. **多语言**（i18n 目录 fnOS 侧已要求）。

## 11.1 决策记录（2026-11-01 已拍板）

| # | 决策项 | 结论 | 影响 |
|---|---|---|---|
| 1 | 访问模型 | **双入口**：网关管管理台 + 独立端口给终端 | 服务端必须同时监听 Unix Socket 与 TCP；`X-Trim-*` 只在网关侧可信 |
| 2 | 服务端技术栈 | **Go + chi** | 单静态二进制、无 cgo、交叉编译进 fpk |
| 3 | 播放内核 | **Media3 主 + libmpv 自动兜底** | 与 5 个生产 APK 的实际做法一致（无一家只用单一内核） |
| 4 | iOS | **硬上 libmpv**（VLCKit 或自编） | ⚠️ 高风险，见下方风险说明 |
| 5 | 首期范围 | **服务端 + 管理台 + TV 端** | iOS/手机后置 |

### 关于「iOS 硬上 libmpv」的风险说明（必须留档）

你选了这条，我按这个方向做，但有三条硬约束必须提前知情：

1. **WSL 里编不出 iOS 版 libmpv**。mpv 的 iOS 依赖链（ffmpeg / libass / libplacebo / MoltenVK）需要 Apple 工具链与 iOS SDK，
   官方构建路径是 macOS + Xcode。可行的绕法是：**用 GitHub Actions 的 macOS runner 编 `.xcframework`，下载回 WSL，
   再由 xtool 链接打包**——这样开发仍在 WSL，但 CI 侧依赖 macOS runner（公开仓库免费）。
2. **预编译 MobileVLCKit 版本滞后**：CocoaPods 上最新是 4.0.0a2（2023-03）。能用，但等于锁死在一个三年前的 ffmpeg 上，
   AVS3 支持存疑。
3. **分发比构建更难**：免费 Apple ID 证书 7 天过期，TrollStore 只覆盖 iOS 14.0–17.0 部分版本（17.0.1+ 永不支持）。
   iOS 端定位只能是「技术验证 + 极客自签」，不能当首发主平台。

**建议的落地顺序**：先做 xtool PoC（验证 SwiftUI + xcframework 链接 + 真机安装三件事），
PoC 通过再投入 libmpv 交叉编译；PoC 失败就退回 AVPlayer（能力覆盖 HLS/H.264/H.265/AAC，够 90% 的直播场景）。

### 关于 AVS3 的能力边界（重要）

- FFmpeg **没有原生 avs3 解码器**，只能 `--enable-libuavs3d`（uavs3d，BSD-3-Clause）。
- uavs3d 只保证 **baseline profile**，且**没有硬件解码**——必然是软解。
- 1080p 软解在盒子上可行，**4K 软解基本不可行**。
- 因此 AVS3 定位为**可选能力**（独立解码包 / 可选内核），不进主链路，否则 APK 体积与稳定性都被拖累。

### 关于 GPL 的决策（默认：接受）

`Media3` 的视频软解扩展（nextlib / jellyfin media3-ffmpeg-decoder）与自编 `libmpv` 都是 **GPL-3.0 / GPL-2.0+**。
一旦静态链接进 APK，整个客户端就受 GPL 约束。

- 若本项目**只自用**或**开源分发** → 无影响，按兼容性优先选型（当前默认）。
- 若将来要**闭源商用/上架应用商店** → 必须改成：自研 LGPL 构建的 FFmpeg + 自写 Media3 Renderer，成本显著上升。
- **现在不影响开发，但这是一个必须在商业化之前回头确认的分叉点。**
