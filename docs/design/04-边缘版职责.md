# 边缘版（edge/）职责重构 · 设计稿

> 状态：**P0 已实现（2026-11-18）；P1–P3 仍是设计**。
> P0 落地的部分（源原文透传、管理台浏览器解析、删除 Worker 内解析器）可与代码逐条对照；
> 其余仍是设计稿，实现前以代码为准。

## 0. 一句话

边缘版不再是"缩小版 litvd"，而是**配置中枢 + 凭据签发**：
能自己解析的客户端（Android）只拿配置与规则，频道、分组、统计、节目单全部在**前端本地算**；
不能自己解析的（iOS）才由服务端下发数据。Worker 只做 CRUD、透传与签发，不做数据加工。

## 1. 现状：三个数字

| 指标 | 现状 | 位置 |
|---|---|---|
| `edge/src/index.ts` | **3113 行单文件**，13 个职责域 | 基础设施/认证/D1 加密信封/设备/管理台/现拉现解析/源/设置/重建/屏蔽/兼容层/播放列表/路由 |
| `bootstrap` 单次 D1 读行 | **≈3.0k**（500 频道 / 800 线路 / 3 万 EPG） | `src/bootstrap.sql.js`，优化前 ≈32k |
| 管理台"预览解析" | **在 Worker 里现拉现解析 m3u** | `src/index.ts:1216-1379` |

第三个数字就是病根。README 写的是"浏览器不能直接拉源（源站不给 CORS），所以由 Worker 现拉现解析"——
但免费版 Worker **每次请求只有 10ms CPU**，解析一份上千条的 m3u 必然越界（1102）。
线上表现与这个推断一致：管理台「预览解析结果」长期是"共 0 条 / 没加载出来"，
源列表里的频道数只能靠 CI 回写的 `sources.last_count` 撑着。

结论：**把浏览器能做的事搬进 Worker，是这套架构最贵的一次错配。**

## 2. 三条分工线

| 层 | 只负责 | 不负责 |
|---|---|---|
| **构建期（CI）** | 抓源清单、取 `x-tvg-url`、缩水护栏、写少量元数据 | 不再生成频道/线路大表（P2 起） |
| **边缘（Worker）** | 设备与绑定、源配置、规则版本、签发（设备 token / 播放地址 / 自解析信封）、CRUD、**字节透传** | 解析 m3u、聚合统计、拼频道 JSON、算"正在播" |
| **前端** | **浏览器**（管理台）：解析源、分组计数、搜索筛选分页、屏蔽影响面<br>**客户端**（Android 已有 `M3uClient`）：拉源解析、过滤、分组、EPG 解析与缓存 | 不做鉴权决策，不落库 |

```
浏览器 ──/admin/*──> Worker ──CRUD──> D1
   └──解析──> /admin/source/{id}/raw（Worker 只透传字节，加 CORS）

Android ──/tv/bootstrap──> Worker（caps=client_parse → 只给信封与规则）
   └──自己拉 m3u + xmltv、自己解析、自己缓存──> /tv/play 都不用调

iOS ──/tv/bootstrap──> Worker（caps 缺省 → 仍下发 channels/groups/now）
```

## 3. 下沉清单（每项都要能量化省下什么）

| 能力 | 现在在哪算 | 重构后 | 省下 |
|---|---|---|---|
| 源 m3u 预览 / 频道清单 | Worker JS 解析（10ms 边界） | **浏览器**（Worker 只透传） | CPU 风险归零；预览从"不可用"变"可用" |
| 频道搜索 / 分组 / 分页 | SQL（`admin/channels`、`tv/channels`） | 前端数组操作 | D1 读行 |
| 分组计数、概览统计 | SQL 聚合（bootstrap `groups`、`adminStats`） | 前端 reduce | D1 读行；省一次往返 |
| 「正在播」 | SQL JOIN，每请求一次 | 客户端从已下载 xmltv 本地算 | bootstrap 读行的大头 |
| 频道表下发 | SQL 拼 JSON（`bootstrap.sql.js`） | 客户端自解析（Android 已有） | bootstrap 响应 0.1~1MB → <4KB |
| 播放地址 | `/tv/play` 查 D1 | 客户端从自解析结果直接取 | 一次往返 + 一次查询 |
| 屏蔽规则 | SQL `json_each` 过滤 | **规则下发，客户端本地过滤** | 同上；点完立即生效不依赖重建 |

**保留在 Worker 的**（无法下沉，或下沉不划算）：
设备注册/心跳（凭据）、收藏/续播（按设备存，需跨端一致）、播放地址签发（自解析模式下不再需要）、
源配置与规则版本、管理台 CRUD、**字节透传**（唯一必须留在边缘的网络动作）。

## 4. 契约变更

### P0（不改客户端，契约只增不改）

新增一个透传端点，替代 Worker 内解析：

```
GET /api/v1/admin/source/{id}/raw        管理台会话
→ 200 text/plain | application/octet-stream
   Access-Control-Allow-Origin: <管理台自身 origin>
   上游响应头（content-type / content-encoding）原样带回
```

约束：
- 复用 `src/net.ts` 的出站校验（拒本机/内网/链路本地/`.local`/`.internal`，跳转逐跳校验）
- 上游体积上限（建议 8 MiB），超限返回 `1001`，**不截断后当成功**
- 只允许 GET；不转发客户端 `Cookie` / `Authorization`
- 透传失败如实返回上游状态码与简短原因，不伪装成"0 条"

`admin/channels-live` 保留但改为**不再解析**：返回 `{ client_parse: true, raw_url: "/api/v1/admin/source/3/raw" }`，
由管理台自己拉文本、自己解析。旧前端拿到这个响应会走"空列表"分支——需要在同一版里改管理台，不能分批上线。

### P1（需客户端发版，能力协商）

`POST /api/v1/device/register` 增加可选 `caps: ["client_parse"]`，存到设备行；`bootstrap` 按该行分支：

| 形态 | 触发 | 响应 |
|---|---|---|
| **lean**（目标态） | 设备 `caps` 含 `client_parse` | `device` / `channels_version` / `client_parse:1` / 加密信封（源 + 规则）/ `epg_url` / `favorites`；**无** `channels` `groups` `now` `sources` |
| **full**（兼容态） | 否则（iOS、旧版 Android） | 与现在一致 |

`channels_version` 语义不变（写点 +1），lean 形态下它是**唯一的**刷新触发器，所以推进逻辑必须覆盖
"改屏蔽/改覆盖/换源"三类写操作（现在 `affectsChannelList` 只覆盖一部分路径，要扩）。

## 5. 落地顺序

每步独立可回滚，**前一步不绿不进下一步**。

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0-1** ✅ | 新增 `GET /api/v1/sources/{id}/raw`（管理台前缀）与 `/api/v1/admin/source/{id}/raw`（原生前缀）透传端点：出站逐跳校验、8 MiB 上限、只 GET、不转发请求头 | `workertest.mjs` 9 条断言：未登录 2001、内网 1001、超限 1001、上游 404 → 4001、字节一致、UA 透传、content-type 保留、no-store |
| **P0-2** ◐ | 源页预览改为浏览器解析（`admin/src/utils/m3u.ts` + `previewSource` 走 raw）；**频道清单 / 分组计数 / 搜索分页未改**——当前 `CHANNELS_MODE=server`，数据在 D1，SQL 分页比全量拉更省 | 线上源页能显示真实频道数与格式；不再出现"共 0 条" |
| **P0-3** ✅ | 删除 Worker 内 m3u 解析器（`parseExtinfAttrs` / `splitExtinfLine` / `normalizeName` / `dedupeKeyOf` / `parseM3uChannels` / `LiveChannel`）；`adminChannelsLive` 退化为返回 `raw_paths` + `policy` | `typecheck` + 两套自测全绿；Worker 侧无 m3u 解析逻辑 |
| **P1-1** | **解析规则对拍**：把 `build.mjs` 与 `M3uClient` 的 dedupeKey / 归一化规则抽成同一份用例表（金样），两边各跑一遍 | 用例覆盖：tvg-id 优先、重名、逗号名、`rtp://`、GBK、分组空值 |
| **P1-2** | `register` 支持 `caps`；Android 上报；`bootstrap` 按 caps 分支 | lean 形态 `bootstrap` 读行 <20、响应 <4KB；心跳链路不受影响 |
| **P1-3** | `affectsChannelList` 扩到屏蔽/覆盖/换源 | 改屏蔽 → 客户端下一跳心跳就重拉 |
| **P2** | CI 在 client 模式跳过频道表 seed（只写元数据 + EPG 地址） | D1 写入行数从数千降到 <100/次；护栏改按"源可达性 + 条目数" |
| **P3** | iOS 补自解析（或明确永久留在 full 形态） | 二选一，写进 README 支持表 |

**先做 P0-1 → P0-3 的理由**：它不碰客户端、不改契约、直接把"预览不可用"这个真实故障消掉，
并且顺手删掉边缘侧最容易触发 1102 的那段代码。P1 才有收益但要等发版，放后面。

## 6. 兼容与回滚

- **全局开关仍在**：`CHANNELS_MODE=server|client`（`build.mjs` 读）决定 CI 是否入库频道表。
  P0 全程保持 `server`，P2 才切；切回只需改环境变量 + 重跑一次。
- **bootstrap 双形态共存**：lean 是新增分支，full 分支代码不动 → 回滚 = 不再给设备标 `caps`。
- **管理台**：P0-2 与 P0-3 必须**同版本**上线（旧前端 + 新后端会拿到空列表）。CI 里 `admin` 与 `edge` 同一个 workflow，天然一起构建。
- **D1 数据不删**：P2 只是停止写入，`channels`/`streams` 表保留，随时可切回。

## 7. 风险与不做的

| 风险 | 处置 |
|---|---|
| **iOS 断层** | iOS 无 `client_parse`，能力协商下自动留在 full 形态；P3 再决定是否补齐 |
| **两套解析规则漂移** | P1-1 的金样对拍是硬前置。现在只靠注释对齐，`M3uClient` 注释里自己就写了"必须与 build.mjs 一致" |
| **上游带 sign** | 客户端每次自己拉订阅 → 签名比 CI 快照更新鲜，是净收益（README 里"98 分钟后过期"的限制在 lean 形态下消失） |
| **多台设备各拉 m3u** | 版本变了才拉（缓存在本地），一天几次；上游限制并发时会互踢，这是已有问题，不新增 |
| **透传被当开放代理** | 必须要求管理台会话；只 GET；不转发请求头；体积上限；出站校验复用 `net.ts` |
| **不做** | 不做 Worker 内缓存层（PPR/Cache API）——免费版 KV/Cache 写入也是额度，且会引入"改了不生效"的新一类问题 |

## 8. 完成标准

- `npm run typecheck` / `npm test`（selftest + workertest）在 CI 全绿
- lean 形态实测：`bootstrap` D1 读行 <20、响应体 <4KB、单请求 CPU 无明显峰值
- 管理台源页预览在**线上实例**能显示真实频道数与分组（这是当前唯一可观测的失败点）
- README 的"支持情况"表与本文一致；`docs/README.md` 索引已登记
- 报告写明：哪些经过真机/线上验证、哪些只有自测覆盖
