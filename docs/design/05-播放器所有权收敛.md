# 播放器所有权收敛（决策稿）

> 状态：决策已定，未实施。配套评审：`docs/review/` 里 2026-11-24 客户端评审 P0-1。
> 这份文档只回答一个问题：**播放器归谁所有**。实现分几步、每步怎么验，写在最后。

## 1. 今天的事实（2026-11-25 复核）

| 事实 | 证据 |
|---|---|
| 有 4 个 `PlayerManager` 构造点 | `PlayerActivity`、`PhoneHomeActivity`、`PhonePlayerActivity`、`LitvApp.player` |
| `LitvApp.player` 从未接管正在播的实例 | 它 `by lazy`，唯一访问点是退后台兜底 `pauseAll` 的 `pause()`；没有任何 Activity 把在播实例交给它 |
| `PlaybackService` 从未启动过 | `instance` 恒 null，`ensureRunning()`/`playerOrNull()` 零调用者（已于 `986956d` 删除） |
| 三个 Activity 的起播逻辑已经漂移 | TV 有 150ms 换台合并 + `PlayRequestGate` + 缓存起播 + 内置源/本地解析；手机首页只有缓存；手机全屏页两样都没有 |
| 每个 `PlayerManager` 构造即注册 `ACTION_SCREEN_OFF` 接收器 | 最多 4 个接收器，只靠 `onDestroy` 兜底 |

结论：**「应用级单例 + 前台服务保活」这套叙事从来没有实现过**，实际形态是「每个页面自己造一个播放器」。文档与代码不一致这件事本身，比任何一个 bug 都更容易误导后来的人（本次评审里已经误导过一次）。

## 2. 两个候选

### A. Activity 作用域单 owner（推荐）

播放器由「当前正在显示画面的那个页面」持有，页面销毁即释放；跨页不保活，进页重建。

- 符合现状：三个页面本来就是各造各的，产品行为也是「进页重建」。
- 改动最小：把三份起播逻辑收敛到一处（`PlaybackCoordinator`），删掉 `LitvApp.player` 与 `pauseAll`。
- 风险可控：退后台停播本来就依赖 `onPause`，删掉那个空转的全局实例不会改变可见行为。
- 代价：旋屏 / 返回再进会重建播放器（现在也是），起播多 0.7~1.5 秒。

### B. Service 单 owner

播放器放进前台服务，Activity 通过绑定拿控制权，`mediaPlayback` 类型 + 常驻通知。

- 好处：退后台可继续播、跨页不重建、旋屏不中断。
- 代价：需要通知渠道、前台服务权限、`stopSelf` 时机、与「退后台就停播」的产品约定冲突；
  真要做得对，还要处理 `onTaskRemoved`、电池优化白名单、Android 14 的 FGS 类型审计。
- 判断：**当前没有「后台继续播」的产品需求**，为一个不存在的需求引入前台服务与常驻通知，是把复杂度换成风险。

## 3. 决策

**采用 A：Activity 作用域单 owner，明确不做后台播放。**

配套三条硬约束：

1. **单一构造点**：全仓只允许 `PlaybackCoordinator` 里出现一次 `PlayerManager(`。
2. **单一用例**：起播/换台/重试/暂停/恢复/停止只在 `PlaybackCoordinator` 实现，页面只发意图。
3. **单一契约出口**：心跳与 QoE 由会话状态变化触发，不再挂在某条分支的成功回调里
   （现在 `/tv/play` 成功才有心跳，缓存起播/内置源/本地解析/时移四条路径全漏）。

## 4. 实施顺序（每步可回滚）

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 删 `LitvApp.player` 与 `pauseAll`；退后台停播只依赖各页 `onPause` | 真机：播放中按 HOME → 3 秒内无声；回前台继续播；`git grep "app.player"` 为空 |
| 2 | 抽 `PlaybackCoordinator`，先只接管 TV 一条路径 | 换台合并、缓存起播、内置源、本地解析四条路径行为不变（对照清单） |
| 3 | 手机首页 / 手机全屏页接同一 Coordinator，删各自副本 | 手机端连按换台不再串台（现在首页没有合并逻辑） |
| 4 | 心跳/QoE 移到会话状态出口 | 四条路径都能在日志里看到心跳 |

第 1 步独立可做、独立可回滚，且**不改变可见行为**；第 2 步起才动真实逻辑，必须在真机上跑
「息屏唤醒 / 快速切台 / 断网恢复 / 换线路」四件套。

## 5. 明确不做的

- 不做后台播放、不加常驻通知、不恢复前台服务（理由见 §2 B）。
- 不在这次收敛里改 `PlaybackPolicy` 参数（那是测量驱动的另一件事）。
- 不动 `resyncWindow()` 的转场路径（已定案：VLC 只同步窗口尺寸）。

## 6. 遗留风险

- 第 1 步之后，若某个页面 `onPause` 里漏了 `pause()`，就会出现「退后台仍出声」——
  这正是当年加 `pauseAll` 的原因。所以第 1 步必须先在真机上确认三个页面的 `onPause` 都真的会停，
  再删兜底；顺序反了就会把兜底删在一个还没接住的路径上。
- **该风险已于 2026-11-25 处理**：兜底换成 `LivePlayers.pauseAll()`（真暂停活着的实例，
  并打印命中数），随后删除 `LitvApp.player`。实测：设置页按 HOME → `命中 1 个` + AudioTrack 消失。

## 7. `PlaybackCoordinator` 接口草案（第 2 步的落点）

这一节只是**接口与搬迁映射**，不含实现，目的：让第 2 步变成「填空」而不是「重新设计」。

```kotlin
class PlaybackCoordinator(
    private val ctx: Context,
    private val prefs: Prefs,
    private val api: Api,
    private val listener: Listener,
) {
    interface Listener {
        fun onState(s: SessionState)          // Idle/Starting/Playing/Degraded/Failed
        fun onChannel(ch: Channel)            // 当前在播的台（OSD 用）
        fun onError(msg: String, retryable: Boolean)
    }

    fun attachSurface(surface: Surface?)      // 页面只交渲染目标
    fun play(ch: Channel, source: PlaySource) // 唯一入口；内部做代际/合并/预算
    fun pause(); fun resume(); fun stop(); fun release()
    fun retryNow()
    fun stats(): EngineStats?
}
```

搬迁映射（谁搬进去、搬完谁就不用管了）：

| 现在的职责 | 现在在哪 | 搬进 Coordinator 后 |
|---|---|---|
| 换台 150ms 合并、`PlayRequestGate` 代际 | `PlayerActivity.playChannel` | Coordinator（唯一实现） |
| 缓存起播（`PlayCacheStore` + `Api.playCache`） | `PlayerActivity` / `PhoneHomeActivity` | Coordinator |
| 内置源/本地解析分支 | `PlayerActivity` / `PhoneHomeActivity` | 参数化为 `PlaySource` 策略，Coordinator 不 if/else |
| 心跳、QoE | 三处 `/tv/play` 成功回调 | Coordinator 的会话状态出口 |
| 起播预算、看门狗、切内核 | 已在 `PlayerManager` | 保持不动（第 2 步不碰） |
| 双图/Surface 绑定 | `PlayerActivity` | Coordinator 只接 `attachSurface` |

**第 2 步的验收口径**：TV 一条路径接上 Coordinator 后，四条起播路径（缓存 / 内置源 /
本地解析 / `/tv/play`）行为与今天逐条一致，且真机跑「息屏唤醒 / 快速切台 / 断网恢复 /
换线路」四件套。**不达标就不往下接手机端**——两份实现并存比三份更糟。
